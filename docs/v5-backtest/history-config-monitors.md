## Where the draft is wrong or contradicts itself

1. **Commit rule, two definitions.** §3.1 says `committed` = "an in-sync quorum holds it"; §4.2 says commit = every member of the in-sync set has it, gated by `minInSync`. Kafka's rule is the second; "quorum" should go.
2. **"Nothing anyone saw is ever undone" (§4.2) vs `committed` without fsync (§3.1).** A correlated power loss of the whole in-sync set loses records that subscribers already saw (H-111). Either state the limit, as v4 did, or gate the high-water mark on fsync.
3. **One fdatasync per batch across all shards (§4.1) vs per-shard segment files (§4.1).** fdatasync covers one file, so this needs either one shared file or one fsync per segment per batch (H-106).
4. **Segment deletion (§4.1) vs N-11.** §4.1 waits for "every replica's fetch position"; N-11 says retention never waits on a replica outside the in-sync set (H-127). Neither names the fsynced snapshot at an offset ≤ HW that deletion actually needs (H-128).
5. **Refusals on retry: §4.3 vs N-07.** §4.3 says a retry gets the first attempt's answer "including its refusal"; N-07 says a refused attempt "is judged afresh on retry". A refusal is never appended to the log, so a new leader cannot have it anyway.
6. **Dedup and validation order.** §4.3 puts dedup before conditions at the leader, but §4.5's `validation` runs where a write enters, i.e. before dedup. During a roll (N-18) a retry of a committed write can be refused (H-091).
7. **"Two members … either member's crash heals" (§4.2).** This holds only with a witness, and shards stay writable only at `minInSync: 1`. Without a witness, "a clean stop is not a leave" leaves 1 of 2 voters: no controller and no writes. Example 01 regresses (H-064), yet §11 phase 3 promises examples pass unchanged.
8. **"Eight wire verbs" (§1, §4.7).** The table has 19 verbs and still lacks RPCs the design depends on:
   - OffsetForLeaderEpoch (§4.2 truncation);
   - the leader's ISR-change request to the controller;
   - member registration/heartbeat to the controller (H-023);
   - metadata snapshot install (N-21);
   - resource create/alter (N-17, §4.5 "online").
9. **Every member a voter (§4.2) vs the n≈100 tier (N-22).** A 100-voter Raft group is not KRaft's design (H-048).
10. **Code lives where the hash does not (§4.5 vs §3.1, §4.3).** Leaders run `rules.write`, ops, `rows.where`, `load` and `partition`, but the metadata log holds only hashes (H-283).
11. **Resource config "online" (§4.5) vs N-17.** N-17 refuses a second creator with different options, and no alter API is named.
12. **"The fold is data's" (§4.3) vs §8 L2's "compact store, no per-record objects".** These are two different fold implementations; SCHEDULE 11e (immutable shared references) is at risk.
13. **N-05 `fresh` reads via read-index.** There is no `fresh` read in §4.5's api, and read-index is a Raft concept with no stated ISR equivalent.
14. **§6.1 #12 "no deleted row comes back: structural".** A `load` read-through re-creates a removed row on the next miss, and a cursor into a reborn cluster resolves to unrelated records (H-062).
15. **Unplaced config.** §4.5's three scopes omit heartbeat/election and lag timing, `rendezvous`, `redial.ms`, `journal.cap`, `signals`, `cache` and `diag` (H-276).

## §10 against the dev-process evidence (Part 4 of the catalog)

**Where the diagnosis fits.**
- The long lanes were the novel mechanisms: V4-55 (8 rounds), V4-62 (5 fix rounds + 8 reviews), V4-60 (6), and the stale-reply fix parked after three reviews, each finding a deeper hole.
- Design-first worked when tried: the V4-37 leave harness found three splits before any fix.
- DECISIONS doubled.
- The golden-trajectory tax is real (V4-19 needed a 200-seed trace diff).
- Fewer, published mechanisms plus model checking is the right direction for L1.

**What §10 misses.**
1. **Where the rounds actually went.** Much of the October effort was L3/L4/surface, not L1: spoke edges (V4-62), the keyed handover read (V4-65), the directory (25 findings), config (26), the door (3 rounds), the example skeptics. TLA+ of L1 alone covers none of these. 21 of the 54 `open` rows above are L2–L4 or surface: cursor identity, dedup head vs committed, validation order, call keys, partial aggregates, code on leaders. The L3 subscription/cursor protocol and L2 dedup/condition semantics need a spec too.
2. **Reviewer capacity was a recorded bottleneck four times:**
   - V4-3's panel was refused by a usage limit;
   - V4-8's panel hit a limit;
   - Fable's weekly limit hit mid-wave 5a;
   - wave 5e ran on Opus alone (Fable spent, Sonnet blocked).
   §10 assumes review rounds are free to schedule.
3. **Parallel sessions collided.** V4-51/52 had to be renumbered at merge; a wave-5f lane was dropped because V4-47 landed the same fix first; 18 commits on 2026-09-22 had no ledger line. Lane ownership and merge discipline are absent from §10.2.
4. **The infrastructure never existed.** There was no git remote, no CI (V4-29 unpushed), WSL2 2–3× perf noise, 9p-mount test budgets and a flaky perf tripwire. §10.2's "full battery runs in CI" and §8.3's pinned runner presuppose it.
5. **Late reviews caught real criticals.** V4-57's second review found a boot-record window; the V4-30 relay hole was real; I-21 was found at HEAD; four independent finders hit M4's critical. "One adversarial review, scoped" (§10.2 #5) would have shipped these, and the v3 record says review-after-green "paid for itself every time".
6. **Monitor and oracle soundness was its own bug class.** It shows up as a dead fault option, vacuous exactlyR and churn sweeps, blind cursors, a tautological monitor and the unsound scoped confirm oracle. v5's trace validation inherits it; make non-vacuity counters and mutation checks a rule.
7. **No swamp guard.** v3's CHECKPOINT sliced M4 into five landable steps. §11 has no checkpoint or abort criterion for a full kernel rewrite, and phase 1 asks for a named test per backtest row (hundreds).
8. **The site is undiagnosed.** It was +37.7k lines in October, with recordings and claims redone per change; it appears in §10.1's table but not in the diagnosis.
