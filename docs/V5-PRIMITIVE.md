# The simplest primitive for fero: a second opinion

Written 2026-11-04 against DESIGN-V5.md (§1-§5, §8, §12), V5-REPLICATION.md and V5-LOG-FIRST-REVIEW.md. Formed from the requirements first, then compared.

## 1. The pick

**The unit is a cell: one replicated, fenced, ordered log of opaque records, with exactly one appender at a time, a snapshot hook, and cursored reads.** The kernel gives a cell five operations and nothing else: `append(bytes[], term) → offset` (refused `stale-term` unless the caller is the leader of that term), `read(cursor) → records…` (from any replica, up to the commit offset, with byte credits), `snapshot(offset, bytes)` (the hook by which whoever folds the cell tells the kernel what covers offsets ≤ i, so the log below can be dropped or shipped to the object store), `change(members)` (Raft's one-at-a-time membership change, learners first), and `lead(member)` (Raft's leadership transfer). Its guarantees are Raft's, unchanged: a committed record is on a majority's disks (or in a majority's memory, or on the leader only: the durability knob is the quorum and fsync parameters of this one unit); the log is a prefix-stable total order; at most one appender per term; and the fencing term rides every append and every cursor. The kernel knows no rows, cells-as-paths, conditions, ops, TTLs, leases, dedup, writer time or selectors. All of that is **the object**: a deterministic library hosted on the leader, given the fold and the uncommitted tail, which decides what bytes to append and what to answer. Scaling is many cells placed by a ring and moved whole; the cluster's own facts are one more cell. This is a Durable Object whose storage is its own Raft log; it is V5's "Raft per shard" with the kernel boundary drawn one layer lower.

## 2. The patterns on a cell

Costs are per operation, steady state. "1 round" = one majority round trip with one fsync, the price of any replicated commit. A client hop is client → any server → leader (2 hops; 1 when the server leads).

| Pattern | How it is built | Cost |
|---|---|---|
| live shared state | an object whose fold is a map of rows; followers fold the same log | write: 2 hops, 1 append, 1 round. Read of a held row: in-process |
| cache with TTL and eviction | the object stamps writer time into each record and appends `remove(ttl|max)` on its tick | one extra append per eviction; no round for reads |
| near cache on clients | a client reads the cell from a cursor for the partitions it follows, drops LRU | 0 rounds; one `read` stream per server pair |
| read-through cache | a miss asks the leader; the object runs `load` once per key, appends with `if: version` | 2 hops + load + 1 round |
| websocket fan-out by room | a room is a partition; a webserver keeps a cursor on the cells of its rooms only, filtered at the serving replica | per message: 1 round at the writer, then one encoded copy per following server |
| pub/sub | a cell with quorum = leader-only and fsync = never, log kept only in memory | 1 hop, 0 rounds; cursors carry the term, `latest` on a new term |
| streams, replay, compacted topics | history retained to a bound; a compacted topic is snapshot + tail, which the kernel already keeps | replay: sequential read of segments; 0 rounds |
| consumer groups | a `#groups` cell: members as leased rows, assignment a pure function of (live members, generation); offsets as rows fenced on the generation | join/leave: 1 round; offset commit: 1 round, batched |
| work queue: claim, ack, lease, dead letter | messages are rows; `claim(n, lease)` is an object op at the leader; ack appends a remove; a lapsed lease is re-claimable; past `deliveries` the object appends to a dead cell | claim: 2 hops, 1 round; ack: 1 round; lease: no round until lapse |
| locks, leader election, fencing | a `#locks` cell: `if: absent | expired` claim; token = claim offset; protected appends carry `{lock, token}`, which the target's object checks against its highest-seen token | acquire: 1 round; fenced write: 1 round; no extra round for the fence |
| counters, rate limits | `incr(n, {min,max})` op at the leader; a window is a row with ttl | 1 round, or 0 rounds with quorum = leader-only for a soft limit |
| leaderboards, live aggregates | `data` operators over the fold on any replica; across cells, each cell's object appends a mergeable partial into a derived cell | per change: fold + view update; cross-cell: +1 round per partial |
| presence | `#sessions` cell with leased rows; rows written `while: session` carry the id; each object follows `#sessions` and removes orphans | renew: 1 round per lease; removal: 1 append |
| invariants (stock, balances) | conditions and ops at the leader against the log-end state, or all affected rows in one partition | 1 round |
| cross-partition transactions | saga: locks in key order, an intent row, fenced steps, intent removed; a later holder finishes an intent | k cells: 2k+2 rounds; readers see intermediate states |
| event sourcing, CQRS projections | history `'all'`; projections are followers folding their own view, or derived cells | 0 rounds for projections on followers |
| derived resources | a reader with a cursor on cell A appends to cell B; its cursor is a fenced row in B, so the fold of B is exactly-once | per record: 1 round at B; cursor stored every batch |
| tapes, forks, replays (fero test) | a tape is a cell with history; a fork is a new cell whose first snapshot is the parent's at an offset (one catalog record) | fork: 1 round in the catalog cell |
| roll, sleep, wake (fero deploy) | `lead()` away, restart, catch up; sleep leaves voters that hold the log only; wake loads a snapshot | handover: 1 round + 1 fsync per cell |

None of these needs a wire verb of its own. Every one is an object (a fold plus a rule for what to append) over the same five operations.

## 3. What this removes or changes in DESIGN-V5, by section

The unit is the same as V5's shard. The cuts are to what the kernel claims and to novel mechanisms that are not Raft.

1. **§4.3 L2 and §4.4 L3 leave the kernel.** The kernel is §4.1 (L0) and the Raft core of §4.2 (L1). Everything in §4.3 (dedup, shape checks, rules, conditions, ops, claim, writer time, row retention, log-end vs committed state) is the standard object, a library shipped with fero, model-checked against a trivial model: "a sequence; one appender per term sees a prefix". V5 says L0-L3 are deterministic and layered; this goes further and keeps L2-L3 out of the safety model, so raft.tla plus a snapshot property is the whole kernel spec.
2. **§4.7 the wire: 28 verbs to about 15.** Delete the `writes`, `methods`, `plan` and `admin` families and `FOLLOW`/`UNFOLLOW`: they are all "a message to the cell's leader, answered after commit", one pair, `ASK`/`ANSWER`, whose payload the object interprets. Keep link (4), raft (7), `ASK`/`ANSWER`, `SUB`/`SNAP`/`DELTA`/`END`/`CREDIT`. Planner hints (§4.2 "The planner") are `ASK`s to the leader with an admin claim; `PLAN`/`PLAN-ACK` go.
3. **§4.4 selectors shrink.** The kernel's subscription is (cell, cursor, credits). `partitions`, `prefix`, `view` and `state` mode (snapshot, then deltas, conflated) are the serving replica's object, which owns the fold. Same bytes on the wire, one fewer kernel concern.
4. **§4.2 "Splits" and "Scaling up and down" rows 5-7, §12.7 "one starting shard, then split": delete.** Children in the parent's term, replicas holding children's messages, cursor lineage, inherited dedup outcomes and fence tokens, the parent's log retained for the children, and the "no split child still needs it" clause of §4.1's drop rule are the one place V5 re-creates the v4 pattern of a novel protocol with many interactions (V5-LOG-FIRST-REVIEW F5/F6 says the same of the log-first draft; CockroachDB's merges "took years"). Replace with: `shards` is fixed at define (default 16, power of two; tiny projects quiesce the rest), cells move whole, and a resource that outgrows its count is re-keyed by the derived-resource library into a new generation with more cells, then the catalog pointer switches under a fence. Slower, copies data, zero kernel mechanism.
5. **§4.2 "Who stands for election": delete the three ranking rules** (rank order, lag step, skew rank). Keep Raft's randomized timers, PreVote, CheckQuorum, and "leaders spread" as a `lead()` transfer policy run by the system object after `settle.ms`. Who wins stays Raft's; who tries first stops being a rule to model.
6. **§4.2 "Log replicas: leading only to repair" (the 3-step protocol): shrink to one rule.** A cell whose leader hosts no object refuses `ASK` with `no-writer`. Bringing a server up and handing over is the planner's or system object's job through `change()` and `lead()`, not a kernel state machine.
7. **§4.3 dedup: replace the floor, the window and the per-hop time budget with Raft-thesis client sessions** (Ongaro 2014, ch. 6): one session row per issuer in the object's state holding (highest seq, outcomes above the acked floor), expiring by writer time. Keep two V5 rules as library rules: a resent attempt's refusal is appended; a first send's is not. Delete "No late arrivals" (time budgets subtracted per hop, forward-only-over-the-original-link): a late copy has seq ≤ highest and is answered from the session or `stale-attempt`, which is already V5's own last sentence of that paragraph.
8. **§3.2 `durability` rungs become two cell parameters:** quorum ∈ {majority, leader} and fsync ∈ {before-ack, async, never}. `persisted` = (majority, before-ack); `memory` (decision 4b) = (majority, async); `none` = (leader, never). `confirm: 'sent'` is an object-level answer timing, unchanged.
9. **§3.1 knobs:** the kernel knows `history` only (what to keep below the snapshot). `rows` and `cache` are object and process knobs, as V5 already says; this just names where they live.
10. **Keep unchanged:** §4.1 L0 entirely (journal, cuts, incarnations, lease epochs, object store, drop rule minus the split clause); §4.2 genesis, `#meta`, healing by the leader with a ring target, failure detection, quiet shards, leave/restart, recovery, routing; §4.5 surface; §5; §6.

## 4. Where it is weaker than V5

- **Big single resources.** V5 splits a hot or large shard with no copy and no downtime, at phase 4. A cell never splits: outgrowing `shards` means a re-key that copies the data and a cutover. For a resource that grows 1000× unpredictably, V5 is better. My bet is that this is rare for a library and common only for the hosted product, where the planner can over-provision `shards` at define time; it is still a real loss.
- **Idle cost at tiny scale.** A resource is 16 quiet Raft groups instead of one. Quiescence makes the wire cost zero, but the Raft state and the catalog rows are 16× V5's for a solo dev project.
- **A seam on the hot path.** The kernel hands bytes to the object and the object hands bytes back; the 3 µs conditional-op target (§8) now crosses an interface. In TypeScript that is a function call; in the Rust phase it is an FFI boundary unless the object is also native. V5's L2 inside the kernel avoids the question.
- **Semantics are only as good as the object.** Dedup, fences, TTL and claim are correct because fero's standard object is correct, not because the kernel enforces them. A third-party object can get them wrong. V5's §4.3 puts them where no user can bypass them. (Users still cannot bypass fero's own object; the risk is fero's, not the user's.)
- **Fewer promises in the spec.** V5's §4.3 pins exact behaviours (which answers are appended, when `unknown` is said). With the object as a library, those become the object's spec, which must be written and checked with the same care or they drift.

## 5. Verdict

**The current candidate is the right unit. Nothing simpler covers the list.** The prompts fail for known reasons: a transactional KV with watches (FoundationDB) has five internal roles and a resolver, and its watches cannot be Kafka; etcd is one group and cannot scale; Calvin needs read sets up front and a global sequencer, which is the rejected log-first shape; CRDTs plus consensus-where-needed is v4, and the evidence is in; dataflow is `data`, a library over a log, not a storage unit; a plain Kafka log cannot hold an invariant without a stateful writer, which is this unit; a Durable Object is this unit with single-copy storage and no replication contract. So: **the same thing under another name, with cuts.** "One ordered log per shard, one writer, Raft" is right. What I would still cut from it, in order of how many bugs each will otherwise cost: splits (§4.2) in favour of a fixed count plus library re-keying; the three election-ranking rules; the log replica's three-step repair protocol; the dedup floor and time budgets in favour of published client sessions; and the kernel boundary, moved down so that L2 and L3 are libraries with their own small models and the kernel's spec is raft.tla plus one snapshot property. The 28 verbs become about 15. What V5 already has right and must keep: §4.1 whole, the leader-run healing with a ring target, `#meta` as one more shard, quiescence, the three retention concepts, one subscribe shape at the surface, and "everything else is a library": this report only takes that last sentence more literally.
