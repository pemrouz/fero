# E-32 (c): every interacting pair, placed

Written 2026-11-10 for the v5 design-space study ([BRIEF.md](../../BRIEF.md)). Question Q-32 in [QUESTIONS.md](../../QUESTIONS.md), parts (a) and (c). Part (b), one composed model of the riskiest crossing, is another agent's, in [crossing/](crossing/); it was still running when this was written, so every pair that only it would hold is marked "pending E-32 (b)".

## 1. What DEV-02 asks

[REQUIREMENTS.md](../../REQUIREMENTS.md) DEV-02: list every pair of mechanisms that read or write the same state. **MUST:** each pair sits inside one model, or is shown independent. **SHOULD:** at most 10 pairs. The pairs come from code: `python3 tools/judging.py pairs` reads each mechanism's reads and writes in [judging/mechanisms.json](../../judging/mechanisms.json) and calls two mechanisms a pair when both touch one piece of state and at least one of them writes it ([judging/pairs.json](../../judging/pairs.json), [judging/PAIRS.md](../../judging/PAIRS.md)).

This file does two things. Section 2 checks the read and write sets behind the pairs and says what was fixed. Sections 3 to 8 place every distinct pair in one of three classes:

- **In a model:** an experiment whose model holds both mechanisms' own rules and lets them interleave. Exhaustive models (TLC, or an exhaustive Python search) are counted apart from seeded simulations and randomized tests of real code, which are named "simulated only".
- **Argued independent:** a written argument that no interleaving of the two can break a property. Each names the shared state, who writes it, when the other reads it, and why that order is fixed. Section 5 holds each argument in full; the pair table gives its short form with the pair's own names filled in. **A second agent should check these arguments** (Q-32 (c)); this file is one agent's work.
- **Open:** neither. Each open pair names the model that would close it (section 7).

"Pending E-32 (b)" is a fourth mark for pairs that only part (b)'s model holds. A few of them reach (b) by a reduction that is reasoned, and say so.

Basis: every class rests on a model (model-checked or simulated, with its experiment), a cited source, or reasoning, and says which. The independence arguments are **reasoned**, not run. The only tool run was `tools/judging.py`. The placement was made by a small script that applies the rules of section 3 and the decisions written in sections 5 to 8; it stays in the scratchpad (`$SP/e32c/`: `models.py`, `classify.py`, `engine.py`, `render.py`), because this task writes only this file and the fix to the read and write sets.

## 3. How each pair was placed

1. **Models first.** A pair is in a model when one experiment's model holds both mechanisms' own rules (not an abstraction standing in for them) and the shared state. Section 6 lists each model, what it holds, its bounds and what it leaves out. Where a model holds the two mechanisms but not the crossing that matters, the pair is not credited to it (for example E-31's follower reload is not credited with the log drop during a slot move; E-22's keyed calls had no fence on the key).
2. **Then part (b).** A pair that only part (b) would hold is "pending E-32 (b)".
3. **Then an argument** from section 5, with the pair's own names filled in.
4. **Otherwise open**, with the model that would close it (section 7). A mechanism that was never built or modelled (the slow-leader rule, planner hints, log replicas, the `memory` rung, the dir lease, F `ldr`, H `side`) leaves every pair open unless an argument above places it without that mechanism's own rules.
5. **Per row.** A pair can differ by row. In ISR and SLOG a Raft mechanism touches only #meta's group, so its pairs with data-path mechanisms are independent there (META1). In V4 the "writer" is the ring's owner under last-writer-wins, so pairs that rely on one writer per log are open there. In BUY the group under a saga is JetStream, whose token check is by convention (E-44), so E-24's model does not hold its saga pairs. In SLOG and OBJ the reduction that brings `controller-commands` × `slot-move` into part (b) does not apply, because their moves do not run on Raft groups.
6. **Simulated only** (E-21, E-22, E-38, E-46) is counted apart. These runs let the two interleave, but not exhaustively; a judge who requires an exhaustive model should move them to open. Their closer is the same model, made exhaustive.
7. **What part (b) has shown so far** is not judged here, with one exception that bears on a pair this file places: its results folder holds one counterexample found while composing ([crossing/results/found-refuse-above.txt](crossing/results/found-refuse-above.txt)). With E-17's refusal path and E-20's session floor in one model, a refusal needs E-20's own stale rule (`refuse.above`), or an attempt that has already committed is later told "refused" (property P3, 6 steps). That is `client-sessions` × `writer-judging`, which this file places in E-20, whose `sess` option has the rule; E-17 had no session floor, so it never needed it. It is a rule the composition must keep, not a new one.

## 5. The arguments

Each argument in full, with its fields in braces; the pair table (section 8) fills them in. "Used" counts the distinct pairs that use it. A second agent checks each one by reading the sources it names.

| Argument | Used | In full |
|---|---|---|
| **HINT** | 74 | Routing hint. {r} reads {v} only to choose where to send a message, or to refresh a routing hint, and the receiver re-checks against its own committed log before it acts ({recheck}). So whatever {w} has written there, stale or new, changes only the number of hops or retries, never an answer or an entry. No order between the write and the read is needed. |
| **ONCE** | 17 | Written once, before any read. {w} writes {v} for {thing} once, in a #meta entry that commits before {thing} can be used; its rules never write that value again ({never}). {r} reads {v} only for {thing} that already exists, so the write always comes first. |
| **META1** | 116 | Disjoint groups. In ISR and SLOG, Raft runs only the metadata group (SPACE 4.1, footnote 4). {a} touches {v} of #meta's own group only; {b} touches {v} of the data partitions (or loglets) only. They never touch the same group's {v}, so no interleaving shares an instance. |
| **FIELDS** | 9 | Disjoint fields. {a} and {b} touch different fields of {v}: {fa}; {fb}. Both are entries in #meta's one log, so each read sees every earlier write in log order, and a write to one field never changes the other. |
| **SMR** | 22 | Rows are a function of the log. {w} writes {v} only by applying committed entries in log order (a pure fold, DEV-07; E-43 measured two `data` versions folding the same records to the same rows). {r} reads {v} at a known offset ({where}), so what it reads is fixed by the log prefix up to that offset; the only interleaving is the log order itself, which each mechanism's own model already explores. |
| **COMMITTED** | 3 | Committed entries never change. {w} changes only the uncommitted tail (a follower cuts a tail that conflicts) or drops a committed prefix below a snapshot. {r} reads only entries at or below the commit index ({where}); a committed entry never changes (Raft's State Machine Safety, Ongaro and Ousterhout 2014, section 5.4.3; E-14's TLC runs check it as LogInv), and the drop is raft-snapshot's own pair. So no append or cut can change what {r} reads. |
| **ACK** | 6 | Fixed by the fsync ack. {s} acknowledges an entry, a term or a vote only after its batch's fdatasync (its rule; `persisted` waits for it; E-29 measured 0 of 10,020 acknowledged batches lost over 2,640 power cuts on a journal of this shape). {r} sends a vote, or counts a replica's entry toward the commit, only on that ack. So {r} reads durable.log only after the write it depends on is on disk. (Under the `memory` rung this order does not hold; that is memory-rung's own pair, K-09.) |
| **LEADERLOSS** | 9 | A step-down is a leader loss. raft-prevote-checkquorum writes group.leader only by making a leader step down (CheckQuorum) or by keeping a follower from standing (PreVote). To {x}, a step-down is the same event as the leader loss in {model}, which holds {x} with leader changes; a refused pre-vote changes nothing {x} reads. So the pair adds no interleaving beyond that model's. |
| **TIME** | 4 | Time is stamped before it is read. writer-time is the only writer of time.writer: it stamps t on a batch before any rule in that batch is judged, and t never goes back (its own rule, E-21). {r} reads t only at the writer, as the t of the batch it is judged in, so the order is fixed. {r}'s safety does not depend on how close t is to real time: {why}. A wrong t only moves when a lapse happens, which is writer-time's own bound (E-21's clock-fault families). |
| **GUARD** | 6 | Checked again at use. {r} reads {v} when it raises a version ({when}). A member or replica that changes after that is still bound by {r}'s own guard at use time: {guard}. So any order between the change and the raise ends with no replica running what it cannot. |
| **PUT** | 2 | Put-if-absent of committed bytes. tier uploads only closed, committed segments and snapshots, put-if-absent under a name keyed by (shard incarnation, offset), and names one in the log only after the put is confirmed (DESIGN-V5 4.1). Committed bytes are the same whoever leads (Raft's State Machine Safety), so two leaders that upload one segment upload the same bytes and the second put is a no-op; only a committed entry names an object, so a deposed leader's upload is never named. {x} changes only who leads. |
| **TIERDROP** | 1 | The drop waits for the upload. A replica drops its log below i only once a covering snapshot's put is confirmed and named, and the segment is uploaded or history allows (the drop rule, DESIGN-V5 4.1, which raft-snapshot reads through store.objects). tier writes an object before it is named and never changes it after. So every drop comes after the upload it needs; the naming entry fixes the order. |
| **RESTART** | 3 | Dormancy is a restart. A group goes dormant only when it is quiet and fully committed, and its dormant record is its term, vote, commit and log end (E-26); a wake loads exactly that, which is the state a replica has after a restart with its disk. To {x}, dormancy and wake are a crash and a recovery with the disk kept, which {model} holds. So the pair adds no interleaving. |
| **BUDGET** | 5 | A budget only delays. tenant-budget reads byte counts of durable.log and only delays a tenant's next appends; it never changes, reorders or drops a byte that {x} holds. A delayed append is the same as a slow client, which every model of {x}'s users allows. |
| **PIN** | 3 | Pinned at load. worker-map pins a group to one worker, and so to one journal, when the process loads the group; no row's text moves a loaded group between workers (SPACE axis M, `kwN`: a journal per worker). So every byte of a group goes through one journal and {x} never sees a group split across two. (If a design re-pins loaded groups, this pair is open.) |
| **SEGMENTS** | 5 | Segments do not change. {j} writes a segment file once, fsyncs it, and never changes it after (files roll by a new file and an unlink); deleting one belongs to the drop rule, which raft-snapshot holds and which reads move.record and meta.forks. {x} reads only segments the journal has already fsynced ({where}). So {x} reads bytes that no longer change. |
| **RECORDER** | 1 | The recorder refers only to written bytes. The recorder records each input before the kernel steps on it, and names bulk bytes by their place in the journal (E-42: every bulk input is in the journal in arrival order). The journal truncates or deletes nothing the recorder's window refers to (it reads recorder.tape: E-42's third format rule). So the recorder refers only to bytes already written, which stay until its window moves on. |
| **SNAPJ** | 3 | A drop never reaches the unflushed tail. raft-snapshot drops entries only below a committed index covered by a fsynced snapshot (DESIGN-V5 4.1); {s} reads the snapshot index only to know which segment files it may delete, and truncates its own file only once the segments that cover it are fsynced. A drop never touches the uncommitted tail or an unflushed batch, so neither can remove what the other still needs. |
| **CREDIT** | 6 | Credits never change a write. admission-credits reads {v} only to count a client's outstanding writes; it never changes a write, its route, its id or who leads. Every outstanding write ends with an answer or at its deadline (A-07's rule: the rest wait in the client and fail at their deadline), and either frees its credit, whatever {w} did meanwhile. So no interleaving can lose or double a write, and none can hold a credit for ever. (F-19's goodput under failover is a performance question that E-39 measured with one leader only: K-18.) |
| **DROPGUARD** | 3 | The drop reads the pin. {w} names snapshots and segments that exist at its #meta entry and pins them in meta.forks; raft-snapshot drops a prefix, and tier deletes an object, only when no fork names it (the drop rule, DESIGN-V5 4.1; both read meta.forks). So a named snapshot is never dropped under a fork, and a fork never names one already gone (it reads the snapshot at its own entry). |
| **TRANSFERSNAP** | 1 | A drop changes no index the transfer reads. raft-leader-transfer reads the target's match index and the leader's last index to decide that the target has caught up; raft-snapshot drops only a committed prefix below a snapshot, which changes neither (a target behind the log start gets InstallSnapshot first, which is Raft's own path). So the order of the two does not matter. |
| **QUIETSNAP** | 1 | A drop changes no index quiet-groups reads. quiet-groups reads the log's end and the commit index to decide that a group is idle; raft-snapshot drops only a prefix below a committed index, which changes neither. |
| **QUIETREAD** | 1 | A pending read keeps the group awake. quiet-groups goes quiet only when no ReadIndex request is pending (it reads group.read), and any message, a read included, wakes a quiet group. So a ReadIndex round always runs with a leader that ticks. |
| **RESTORETIER** | 1 | The restore reads immutable objects. The restore reads only objects that tier named in a committed entry at or below the backup position; tier never changes an object once put (put-if-absent), and the restore mark is its own object in the manifest. So the restore reads bytes that no longer change. |
| **TIERWIPE** | 1 | A wiped replica cannot upload. tier uploads only from the leader and only committed segments; a wiped replica rejoins as a new, empty replica (disk-incarnation's rule) and cannot lead before it holds every committed entry (Raft's vote rule; E-14c and E-37). So tier never reads bytes a wipe removed. |
| **FENCEDOOR** | 1 | The certificate opens the door only. cluster-credentials gates the door with the secret and the member's certificate; every role (voting, leading, serving) is decided by meta.members and the group's own config, never by the certificate. So between a removal and its revocation, a removed member can connect but holds no role, and no safety property depends on the order. |
| **SESSIONREG** | 1 | One lapse, in #sessions' one log. client-sessions and presence-rows both keep their sessions in the registry #sessions, whose single writer orders every renewal and lapse. client-sessions' safety holds for any lapse time (E-20: an expired session's copies are answered `unknown` and never judged afresh); presence-rows removes rows only after the lapse has committed there. So each sees the same lapse at a fixed log position. |
| **TIERHIST** | 1 | Each drop is allowed by the setting at its time. tier reads `history` at each drop decision; the drop also needs no slot move or fork to read the segment (it reads move.record and meta.forks). An alter only changes which later drops are allowed; a drop never happens unless the setting in force at its own log position allows it. A reader whose cursor falls below a shortened history is told `expired` by the holding group's leader (A-06), which is what the alter asks for. |
| **NAMEREFUSE** | 1 | One name, one record. meta-catalog and forks both write new resource records into #meta's one log; a second create under a name that exists is refused by meta-catalog's rule, and a fork's record is a new name. Records of different names share nothing; the same name is decided by #meta's log order. |
| **PROPOSE** | 15 | A proposal decides nothing. {r} reads {v} only to pick what to propose ({what}); the protocol that acts ({actor}) checks its own guards against the committed logs before each step, and its model holds it from any start at any moment. So a stale or new value only changes what is proposed. |
| **LANES** | 2 | Fixed per project. The lane count and its hash are fixed for a project when it is made (G `lane`: the count never changes), so lanes writes lane.map once, before any write is routed; route-forward reads a value that never changes after. |
| **CLOCKS** | 1 | A reading is an input. controller-sessions only delivers peers' clock readings into link.clocks; writer-time takes each reading carried forward by its own monotonic clock and stamps max(last t, median). Who carries a reading, and how late, is an input that E-21's families already vary (stale and delayed readings), not a new interleaving. |
| **FOLDEND** | 5 | The new writer folds to the end first. In RLOG the new writer folds to the log's end before it writes, and the log group takes an append only with the latest committed writer epoch (A-14; E-16's RLOG model shows both needed). So {x} stamps or judges from the last committed state, and two writers never both append. |
| **LOADS** | 1 | Load reports decide nothing. split-record reads load.report only to choose where to split; the split's own nine rules hold for a split at any moment and any key (E-17b), so a stale or new report only changes which split is made. |
| **VERSIONFOLD** | 3 | The version is fixed by the offset. The fold reads the version in force at each entry's own offset, and a fold-version entry is itself a committed entry at an offset; a replica that cannot run that version refuses to serve (fold-version's rule). So the version an entry is folded under is a function of the log prefix, and no interleaving beyond the log order exists (E-43 measured two `data` versions folding the same records to the same rows). |
| **READSTORE** | 2 | Committed and immutable. {r} reads a stream that its writer has acknowledged as stored, in stream sequence; JetStream never changes a stored message or its sequence (cited: JetStream's documentation). So {r} reads a fixed prefix. |
| **TWOPATHS** | 1 | Two paths, no promise between them. The `none` rung is a second delivery path that never enters the log and promises nothing about order against it (P-06: best effort). On BUY it is core NATS beside JetStream; nothing either reads is written by the other. |
| **ROWDIS** | 1 | Different replicas. fold-leader writes the rows of the leader and its warm standby; fold-lazy writes the rows of the other replicas, each its own copy. They never write the same replica's rows, and each is a fold of the same committed log. |
| **OWNKEY** | 7 | Disjoint keys under one log. {a} and {b} write different records of {v} ({fa}; {fb}), each as an entry in #meta's one log, and neither reads the other's records. {extra} |
| **CUT** | 3 | The cut is persisted in order. {s} writes a cut record before entries that replace a follower's tail (its rule; etcd's WAL does the same) and, after a crash, replays to its last valid record. So raft-log's tail cut reaches the disk in the order it happened, and the log raft-log reads back after a restart is the log it last acknowledged. |
| **DORMJ** | 1 | The record summarises acked bytes. dormant-groups reads durable.log only when the group is quiet and fully committed, to write its small record; by then {s} has acked every entry of the group (argument ACK) and never changes an acked entry. So the record summarises bytes that no longer change. (Under the `memory` rung an ack may not be on disk: memory-rung's own pair, K-09.) |
| **TABLEROUTE** | 3 | Slots are fixed; the table only routes. consumer-groups assigns slots to members by a pure function of the live members and the generation over the resource's fixed slot ids (catalogue); it reads slot.table only to know where to read each slot, and reading goes through subscribe, which re-checks at the server (E-31). So whatever {w} writes there changes only where a member reads from, never which member owns a slot or what it commits. |
| **DIRSTORE** | 1 | The directory only cleans a hint. meta-directory reads store.objects only to decide when a group's record may be deleted ('its history is safe'); the record is a routing hint (catalogue: the group's own log is the truth). So an upload seen early or late only moves when a hint is deleted. |
| **KEYROUTE** | 1 | Where the call runs decides nothing. leader-calls reads the key table only to send a keyed call to the host that leads it; the claim is judged at the writer of #calls (caller-keys' rule), so where the call runs changes no outcome (E-22: U `ldr` buys no safety). |
| **SNAPEPOCH** | 1 | The epoch is folded state. A restore loads the backup and then writes each slot's new epoch, above the mark, before any write is taken (E-33's rule). raft-snapshot reads a slot's epoch when it cuts a snapshot at a committed offset, so a snapshot cut after the restore's epoch entry holds the new epoch and one cut before holds the old; like any folded state, the epoch is a function of the log prefix (argument SMR). |
| **PINGSET** | 1 | Pings are per member pair. link-pings reads group configs only to decide which member pairs to ping (one ping per pair, catalogue); a pair joins once a config naming both commits. A stale config only delays one gone mark; every rule that acts on a gone mark re-checks on its own links (E-16), so no order between a config change and the ping set breaks a property. |
| **RANGEHINT** | 3 | A stale range is refused at the range. two-phase-commit reads range.table to find the range of each key; the range's leader checks that the key is inside its range before it takes an intent (TiKV's KeyNotInRegion, cited from memory), so a stale table costs a retry and never an intent in the wrong range. |
| **MEMBERPLACE** | 1 | Placement sees the marks in log order. meta-catalog reads member records only to place a new resource's first group, in a #meta entry; it sees every earlier record and mark in #meta's one log and places on no member marked gone. A member that goes after is replaced by healing, whose own pair with the member's marks is E-16's. |
| **ROWS2** | 3 | Different replicas. {r} reads the rows of the leader (judging, copies and lease reads run there); fold-lazy writes only the rows of the other replicas. They never touch the same replica's rows. |

**The arguments that broke**, each with the interleaving it did not consider:
1. **META1, where the "data side" keeps its own state in #meta** (29 distinct pairs, 36 row-pairs, in ISR and SLOG). META1 says the Raft mechanism touches only #meta's group and the other mechanism only the data partitions. That is false for six mechanisms whose state the catalogue itself puts in the metadata group or the controller's log: controller-commands, isr-set, eligible-leaders and leader-epoch (ISR), and loglet-chain and writer-epoch-slog (SLOG). Their records are #meta entries, so the two do share #meta's log. Missed: a #meta leader change, snapshot or voter change between the controller's write of a record and a partition or writer acting on it. Safety then turns on "the data side acts only on committed #meta records", and no rule in this study says that. Closes with the row's own model (ISR, SLOG). META1 still holds for the other ISR and SLOG pairs. For meta-directory's three pairs there it is HINT that holds, not META1, because the directory is itself a #meta record.
2. **SMR, for writer-time** (4 pairs, 35 row-pairs: #85, #149, #364, #769). Missed: a leader change with an uncommitted tail. writer-time reads folded rows (its read set), and rows stop at the commit index. A new leader cannot commit the old leader's tail before its own first entry commits (Raft, section 5.4.2), so it can stamp a batch below the t of that tail, and t goes back along the log. E-21's group "commits at once", so it never had such a tail. Closes with WTAIL, or the row's own model in ISR, SLOG and OBJ. If writer-time really reads the log end, as DESIGN-V5 4.3 writes ("max(last t in the log, ...)"), then mechanisms.json has the wrong read set, and the pair is writer-time × raft-log, open on the same model.
3. **DROPGUARD** (3 pairs, 47 row-pairs: #63, #104, #134). Missed: there are two logs. The pin is a #meta entry. The drop is decided at the parent group (and the tier's delete at the store), each reading its own copy of `meta.forks`. The fork learns that a snapshot exists from the parent's state, not from #meta. So: the fork reads that S exists; the parent reads no pin and drops S; then the fork's entry commits, naming S. Closes with FORKPIN.
4. **RESTORETIER** (#105, 16 row-pairs). Missed: the tier writing after a restore. Objects are named by (shard incarnation, offset) (DESIGN-V5 4.1). A restore raises slot epochs and the session generation (A-08), not the shard incarnation. So when the restored group uploads a segment at an offset the old history already uploaded, the put-if-absent does nothing, and the log names the old history's bytes. Closes with RESTORENAME.
