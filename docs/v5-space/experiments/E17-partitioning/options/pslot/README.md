# pslot: slot moves in groups that belong to the project

**What it is.** The candidate MIN-P (SPACE G `pslot`). Groups belong to the project, not to one resource. A group holds (resource, slot) pairs from any resources with equal `copies` and durability. A new resource's slots start inside an existing group, and slot moves split them off under load. Precedents SPACE names: TiKV PD's cross-table region merge and CockroachDB's span-config coalescing. The partition mapping (P) is slot's: fixed slots, one move protocol, positions `(slot, sequence)`.

**The model:** [model.py](model.py). It is slot's model ([../slot/model.py](../slot/model.py)), with the one thing pslot changes:
- p is a partition of resource P, q one of resource Q. **Both sit in slot 0 of their resource, in one shared group.** So a slot is named `(resource, slot number)`, and two slots in one group can share a number.
- Every entry of the move protocol must therefore say which resource's slot it is about. In slot's model a group holds one resource, and the slot number is enough. Here each entry's resource is its own update (`res`), as HARNESS.md asks for every field of an entry. **Dropping it leaves the resource out:** the entry then names "slot 0" of the group, and it applies to slot 0 of every resource there. That is what a group does if it keeps slot's per-resource code unchanged. The ablation then says which entries really need the name.
- A position is `(resource, slot, sequence)`. The resource in a position is a harness artefact (property P2 compares positions across partitions; in fero a position is read within one resource), so it is not counted as a rule.
- The bound's layouts read as for slot: `grow` moves P's slot 0 out of the shared group G0 into G1; `shrink` moves it back into the shared group; `both` writes to both resources while P's slot moves.

**Left out, on purpose:**
- Everything slot's model leaves out: the slot table in `#meta`, incarnations and epochs (unclean recovery).
- **The placement guard** "a group holds only resources with equal `copies` and durability". It is a guard of whoever picks the target group. No property here can see it break (the harness has no durability or replica count), so it is reasoned: 1 rule in the controller, not in the move.
- **Resource creation inside a running group.** A new resource's slots appear in an existing group by one entry in that group's log. The harness has no property that a duplicate or misplaced create would break beyond what `#meta` already decides for MIN (where a create makes a new group), so it is reasoned, not checked: 1 rule (the entry), the same order of cost as MIN's group create.
- **Group create and delete**, as for every option here. One hazard is new to pslot (reasoned): a resource created into a group that is being emptied and deleted. A group is deleted only when its committed log holds no slot, and it takes no create once its delete is in its log: the two kinds of rule again, about 2 rules, outside this harness.
- **Moving several slots as one move** (a resource's whole slot set split off at once): with one partition per resource here, one move is one slot.

**Results** (model-checked; [../../results/pslot-ablation.json](../../results/pslot-ablation.json); every rule with its trace in [../../../E17b-partitioning-part2/results/summary.md](../../../E17b-partitioning-part2/results/summary.md); part 2's README is [../../../E17b-partitioning-part2/README.md](../../../E17b-partitioning-part2/README.md)):
- **30 of the 80 rules are necessary: exactly slot's 26, plus 4 that name the resource.** Every rule slot keeps, pslot keeps, and nothing else of the move is needed.
- **The 4, one per entry that says who holds a slot or which move this is:** `exporting`, the fence, the final copy and `open` must each name the resource, not only the slot number (`export.res`, `fence.res`, `final.res`, `open.res`). Without any one, the step that acts on the entry cannot tell P's slot 0 from Q's: it fences, copies or opens the other resource's slot 0. The shortest traces: a fence that names only "slot 0" lets B copy and open Q's slot 0, and P's is never handed over (L7 in 5 steps); an `open` that names only "slot 0" opens Q's slot 0 at B while G0 still holds it (P6 in 8 steps).
- **Not needed:** the resource name on `importing`, the bulk copy and every give-up entry (they are not in the core, or they name the move, and the move's name already points at a named `exporting`).
- **The count of beyond-slot rules is the cost of G `pslot` over G `shard`:** 4 rules, all of one kind (name the resource in each move entry). SPACE §2 says "0 beyond P `slot`"; the model says 4, which is "0 new mechanisms" but not 0 rules.
- **Mutants:** 59; 43 caught, 16 equivalent (each swaps two field updates of one entry), none survived.
- **States:** the same as slot's at every bound, as written (22,797 on `grow`) and in the smallest model (1,086 on `grow`, 487 on `twice1`): with the names in place, sharing a group adds no behaviour. The greedy pass is slow, though: with some names dropped, the wildcard entries make the model up to 1.4 million states.
- **Reverse greedy order** (`pslot-rev`, [../../results/pslot-rev-ablation.json](../../results/pslot-rev-ablation.json)): 30 rules again, with N in the fence (`fence.N`) in place of the carried sequence (`final.seq`), the twin part 1 found for slot. The 4 names are the same.
- **A bigger bound** (`readback`: grow, shrink back, the reader on, two writes; [../../../E17b-partitioning-part2/results/extra.txt](../../../E17b-partitioning-part2/results/extra.txt)): `pslot`'s set holds; `pslot-rev`'s fails L7 in 17 steps and needs "fence a move once" (`fence.once`) back, exactly as part 1's `slot-rev` does: after a move and a move back, a stale fence of the first move with a new N closes the slot again. So 30 to 31.
- **The give-up path, one decider** (`pslot+abort`, [../../results/pslot+abort-ablation.json](../../results/pslot+abort-ablation.json)): B's `abort` and `importing` pinned, warm-started as part 1's `slot+abort` was (every bound held with the warm set). **40 kept: the core 30, the 2 pinned, 7 give-up rules and 1 undecided** (`abort.imp`, undecided in `slot+abort` too). The 7 are slot's 5 (`open.noabort`, `abort.noopen`, `unfence.abcom`, `unfence.fen`, `unfence.append`) and 2 more names: B's `abort` and A's `unfenced` must name the resource (P6 in 10 steps on `shrink` without either). `export.res`, decided necessary in the core, is undecided in this bigger model (kept). So **39 to 40**, against slot's 33 to 34: 6 naming rules in all.

**The probe `pslot-fused`** ([fused.py](fused.py); [../../results/pslot-fused-ablation.json](../../results/pslot-fused-ablation.json)): the same option with the move's entries fused the way CockroachDB's split fuses them. A's first entry is the fence (the decision and the fence at once, as a split entry is); B's one entry is the final copy, which also opens the slot (as a split's init does); no `importing`, bulk copy or ready report; the copy is taken at the fence. It is a probe of the move's shape, not a candidate:
- **24 of 35 rules necessary**, the same 24 in reverse order: fixN's 13, plus 11. Of the 11, 2 name the resource (`fence.res`, `final.res`), so **the fused move itself is 9 rules beyond fixN**: no write once fenced; fence only a slot you hold; the fence entry; copy only from a committed fence; carry the rows and records, the outcomes, the token and the sequence; the copy entry. A fused slot move in slot's per-resource groups would then be **22 rules**, 4 fewer than slot's 26 (reasoned: this model less its 2 naming rules; not run on its own).
- **Mutants:** 45; 34 caught, 11 equivalent, none survived.
- **With a working give-up path** (`pslot-fused+abort`, B's abort pinned, one decider): **31 rules, none undecided**: the core 24, the pinned abort and 6 (B never copies once it aborted, B aborts only while its log has no copy, A reopens only on B's committed abort, only for a move it fenced, with an entry that names the resource and says so). Less its 3 naming rules: **28** for a fused slot move with a give-up path, against 33 to 34 for slot's one-decider move.
- **States:** as written 1,799 (`grow`) to 4,241 (`deep`), against 22,797 to 62,653 for the drafted shape; smallest 44 to 540; with the give-up path at most 4,241.
