# E-46: the TypeScript port of etcd raft as a real key-value store, checked by Maelstrom

**Question (Q-46).** Does the TypeScript port of etcd raft (E-10), run as real processes, give a linearizable key-value store under partitions?

**Decides** (QUESTIONS.md §10): trust in every `port` row (MIN, MIN-TS, MIN-P, LEAN, RLOG, DRAFT, CELL, LANE, SPLIT): DEV-04, DEV-05, TEST-10, TEST-13. E-10 checked the port's Raft steps byte for byte in one process. Nothing had yet checked it end to end, with a log, a state machine, reads, and real message passing between processes.

**Threshold** (QUESTIONS.md): every clean run valid, and the planted bug caught → the port carries a real store. A real anomaly → a bug in the port or its host, root-caused before any `port` row is rated.

## The answer

**Yes. The threshold is met.** All measured here; the table is [results/runs.md](results/runs.md), one JSON line per run is [results/summary.jsonl](results/summary.jsonl).

- **Every clean run is linearizable.** 26 clean runs of Maelstrom's `lin-kv` workload, 100 s each, 3 and 5 nodes, with a network partition starting or healing about every 3 s and a node frozen by SIGSTOP for 0.2 to 3 s about every 4 s. Reads went through ReadIndex, through the log, or a random mix; 4 runs also compacted the log every 20 entries, so lagging followers were caught up by snapshot. Knossos (Jepsen's linearizability checker) found every key of every run valid, and Porcupine (a second, independent checker, run here on the same histories) agrees on every key. In all: 55,167 operations that succeeded (25,625 of them reads), 350 elections (9 to 20 per run), 376 partitions that cut at least one link, 428 pauses (731 s frozen in all).
- **The replicas agree byte for byte.** Each node hashes the entries it applies. At every index that two or more nodes logged (1,563 points), the hashes match: 0 mismatches. No node ever threw (no re-apply, no gap, no raft panic).
- **The checkers catch the planted bug every time.** With a follower answering reads from its own state (no ReadIndex), Knossos marked the run invalid in **8 of 8 runs**: all 6 with partitions and pauses, and both 60 s runs with no faults at all. Porcupine flags exactly the same keys in every run. 29 of the 33 keys that had reads failed (every one on 3 nodes, 15 of 19 on 5 nodes), each time on a read that returned a value Knossos could not place after the operations that had already finished ([results/planted-bug-failures.txt](results/planted-bug-failures.txt)). A second, subtler planted bug (a leader that has been replaced but has not noticed yet answers reads from its own state) left a wrong read in only 1 of 4 runs at the same load; Porcupine flagged that run in 0.5 s, while Knossos was still searching after 18 minutes (see The planted bugs).
- **Snapshots work end to end.** In the 4 compaction runs the leaders sent 143 snapshots and followers restored 99; every one of the other 44 is accounted for (1 lost to a partition and sent again later, 42 repeats of a snapshot the follower had just restored, 1 the follower no longer needed), and every receipt was acknowledged ([results/anomalies/snapshot-audit.txt](results/anomalies/snapshot-audit.txt)). This is the part E-10's fuzz never ran: it never compacts, and its mutation run left `CreateSnapshot` and two snapshot-restore cases unguarded.
- **Every anomaly was traced. None is in the port.** Four came up (details below): one late reply after the test ended (harmless timing); more snapshots sent than restored (a choice in this node wrapper, harmless); reads in only half the keys (a Jepsen generator limit, fixed for batch F); and Maelstrom 0.2.4 cannot pause or kill a node (worked around with an outside pauser; kills not run).

## Words used here

- **Maelstrom** is Jepsen's workbench for small distributed systems. It starts each node as a real OS process, talks to it by JSON lines on stdin and stdout, routes every message between nodes through its own simulated network (which can delay, reorder and cut links), and runs clients against the nodes. At the end it checks the clients' history.
- **lin-kv** is Maelstrom's workload for a linearizable key-value store: clients `read`, `write` and `cas` (compare-and-set) small integer keys. Each key's history is checked on its own by **Knossos**, Jepsen's linearizability checker.
- **Linearizable** means every operation seems to take effect at one instant between its call and its reply, in an order every client agrees on. A read never returns an older value than one that some finished operation already showed.
- **ok / fail / info.** `ok` means the operation surely happened. `fail` means it surely did not (a definite error, such as "no leader" or "cas: value did not match"). `info` means the client does not know (a timeout); the checker must allow both outcomes.
- **ReadIndex** is etcd raft's way to serve a read without writing to the log: the leader notes its commit index, confirms by one round of heartbeats that a majority still follows it, and the node answers once it has applied up to that index. A **log read** instead puts the read into the log as an entry and answers when the entry is applied.
- **Partition**: Maelstrom's nemesis (fault injector) cuts links between nodes: one node off, a clean majority and minority, or a ring of overlapping majorities. Clients are never cut off. **Pause**: the node's process is stopped with SIGSTOP and continued with SIGCONT, as a long GC pause or a stalled VM would.
- **Election** here means a term in which some node became leader (counted from the nodes' logs).
- **Snapshot** (MsgSnap): when the leader has dropped the log entries a lagging follower needs, it sends the whole state machine instead.

## Method

### The node ([node/node.ts](node/node.ts), 273 code lines)

One process is one raft replica. It imports E-10's port unchanged (`../../E10-raft-port/port/src/index.ts`; the hashes of the port files used are in [results/port-sha256.txt](results/port-sha256.txt), and they still match the port today) and drives a `RawNode` exactly as [USAGE.md](../E10-raft-port/port/USAGE.md) says: tick, step, and for each Ready persist, send, apply, advance.

- **Raft settings:** etcd's `MemoryStorage` (the log in memory), a tick every 50 ms, `ElectionTick` 10 (so 0.5 to 1 s with etcd's jitter), `HeartbeatTick` 1, PreVote and CheckQuorum on, `ReadOnlySafe` (no leases), synchronous storage (not `AsyncStorageWrites`). The election jitter comes from a seeded generator (`E46_SEED` plus the node's index).
- **The wire:** each raft message is one Maelstrom message, its fields copied as they are (absent fields stay absent), bytes in base64.
- **The state machine:** a map from key to value. A `write` or `cas` becomes a log entry `{id, op, key, ...}` proposed through the node that got the request (a follower's proposal is forwarded by raft to the leader). Every node applies every entry; the node that got the request answers when it applies the entry with that id. `cas` on a missing key answers error 20, on a different value error 22; both are definite, and decided in the log order.
- **Reads, five modes** (`E46_READ`):
  - `readindex`: `RawNode.ReadIndex(ctx)` with a unique context; the answer comes when the ReadState for that context arrives and the node has applied up to its index.
  - `log`: the read is proposed as a log entry and answered when applied.
  - `mixed`: each read picks one of the two at random (seeded).
  - `buggy`, **the planted bug**: a follower answers at once from its own state, with no ReadIndex. The leader still uses ReadIndex.
  - `leaderlocal`, **a second, subtler planted bug**: a node that believes it leads answers at once from its own state (no ReadIndex and no lease); followers use ReadIndex. This is wrong only while a deposed leader has not yet noticed.
- **Refusals:** a proposal that raft drops (`ErrProposalDropped`: no leader known, so it was neither appended nor forwarded) and a ReadIndex while no leader is known answer error 11, which is definite. Nothing else answers with an error: a lost request times out on the client side and is recorded as `info` (indefinite) for writes and cas, and as `fail` for reads (Maelstrom's rule: a read changes nothing).
- **Compaction** (`E46_COMPACT=20`, batch C only): every 20 applied entries the node snapshots the state machine with `CreateSnapshot` and compacts the log to 5 entries behind, so a lagging follower must be caught up by MsgSnap. Maelstrom's network gives no delivery report, so the leader reports each snapshot as finished when it sends it; a lost one is resent after the follower rejects the next append.
- **An extra check besides Knossos:** every node logs a running hash (FNV-1a) of the entries it has applied, every 50 indexes (and at each snapshot it restores). After the run, [summarize.py](summarize.py) checks that every node has the same hash at every index logged by two or more nodes.

### Pauses ([node/pauser.ts](node/pauser.ts))

**Maelstrom 0.2.4 does not offer pauses.** It accepts `--nemesis pause` and does nothing with it: Jepsen's `db-generators` (`jepsen/nemesis/combined.clj`, lines 108-109 in the jar) emits pause operations only when the database implements `jepsen.db/Pause`, and Maelstrom's database (`maelstrom/db.clj`) implements neither `Pause` nor `Kill`. (Read from the jar's own source; a first trial run's history had no pause operation.) So an outside script pauses real processes: each node writes its pid at init; from then on, after a random gap (exponential, mean 4 s), the pauser stops one node with SIGSTOP for 0.2 to 3 s (uniform), then continues it. Half the pauses hit the node whose role file says it leads (as Jepsen's "primaries" target), the rest a random node. A paused node reads nothing; Maelstrom queues its messages and delivers them late. Pauses stop 5 s before the end of the test. Every pause is logged with its time ([results/runs/](results/runs) has one log per run).

Kills (crash and restart) are not run: the log is in memory, so a restarted node would have forgotten its vote and log, which Raft does not allow. E-10's restart fuzz covers restarts from a kept log and HardState.

### The runs ([matrix.txt](matrix.txt), [run-one.sh](run-one.sh), [run.sh](run.sh))

Every run: Maelstrom `test -w lin-kv`, `--rate 50` (operations a second, all clients together), `--concurrency 4n` (4 client threads per node; batch F: 2n), node-to-node latency exponential with a mean of 5 ms (so messages on one link reorder; Maelstrom keeps client-to-node latency at zero), `--nemesis partition --nemesis-interval 3` (a partition starts or heals about every 3 s), plus the pauser. Runs last 100 s (batch D's two no-fault runs: 60 s, no nemesis, no pauser).

| Batch | What | Runs |
|---|---|---|
| A | 3 nodes; reads `readindex`, `log`, `mixed`; seeds 1, 2, 3 | 9 |

| C | compaction every 20 entries (snapshots); `mixed`; 3 and 5 nodes; seeds 1, 2 | 4 |
| D | the planted bug (`buggy`); 3 and 5 nodes; seeds 1, 2, 3, with partitions and pauses; and one 60 s run each with no faults at all | 8 |

**The second checker.** Maelstrom checks each run with Knossos. Every history was also checked with Porcupine v1.3.1 (Go; [tools/porcupine/](tools/porcupine)): [hist2json.py](tools/porcupine/hist2json.py) pairs each call with its answer (a definite failure is dropped, as Knossos does; an `info` or unanswered operation may take effect at any time after its call, or never), and [main.go](tools/porcupine/main.go) checks each key against a compare-and-set register that starts empty, with a 60 s limit per key. [tools/stale_witness.py](tools/stale_witness.py) adds a third, weaker check that a person can redo by hand: a read that returned v, sent after some write finished, when no operation that could have written v was open after that write's call.

Maelstrom has no seed option, so its own choices (which partition, which client operation, each latency) differ from run to run and cannot be replayed. The seeds fix only the election jitter, the read-mode choice and the pauser. Each batch held the shared heavy lock once, for 10 to 30 minutes (batch E: 27 minutes, 18 of them in one Knossos search that was then stopped; see The planted bugs).

### The planted bugs

**Bug 1, a follower reads its own state** (batch D): 8 of 8 runs invalid. One example, bug3-s1, key 0 ([results/planted-bug-failures.txt](results/planted-bug-failures.txt)): a cas from 4 to 3 finished at 5.810 s; a read sent at 5.819 s, after it, returned 4. Knossos: "can't read 4 from register 3". Only keys that had reads can fail (anomaly 3): on 3 nodes every such key failed, on 5 nodes 15 of 19; in the two no-fault runs only one key had reads, and it failed. So the bug shows even with no faults: the node that took a write answers when it applies the entry, another follower applies it a few milliseconds later (when the next append or heartbeat brings the new commit index), and a read served by that follower in the gap is stale (bug3-nofault-s1, key 0: a cas from 4 to 2 through n1 finished at 4.928 s; a read through n0 sent at 4.930 s returned 4).

**Bug 2, a replaced leader still reads its own state** (batch E, 4 runs at `--rate 50`; [results/planted-bug-2.txt](results/planted-bug-2.txt)). Caught in **1 of 4** runs. This bug is wrong only in a short window, and the window is what decides whether a run shows it:

- **The window opens in every run, but briefly.** Maelstrom's network journal has one clock for all nodes, so [tools/journal_deposed.clj](tools/journal_deposed.clj) can tell when a node still acts as leader in term T after another node has started leading in a later term. That happened 9 to 13 times per run, and such a "deposed" leader answered 12 to 30 reads per run.
- **Three runs: every such read was still right.** No write to the read key finished inside the window, so the old leader's value was still the current one. Knossos and Porcupine both say valid, correctly: the history holds no wrong answer.
- **stale5-s2: a wrong read.** n3, still acting as leader in term 8 after term 9 had begun, answered a read of key 9 with 0. The read was sent at 54.852 s; a write of 3 had finished at 54.801 s, and no operation that could have written 0 was open after that write was called. That is a proof a person can check from the history ([tools/stale_witness.py](tools/stale_witness.py)). Porcupine marks key 9 not linearizable in 0.5 s. Knossos, inside Maelstrom, found the same read (its search report names it), but its search had not ended after 18 minutes, so I stopped it to free the shared lock (key 9: 135 operations, 11 of them with unknown outcome).
- **Why the window is short: CheckQuorum** (reasoned from the port's code). A leader cut off from the majority checks its quorum every `ElectionTick` (0.5 s) and steps down at the first check that finds the majority silent, so 0.5 to 1 s after the cut (`tickHeartbeat` in `raft.ts`). The majority cannot elect a new leader until its own election timeout runs out, 0.5 to 1 s after the last heartbeat (PreVote, and the lease check `inLease`). So the two overlap for at most a few hundred ms, and a write on the very key a client then reads at the old leader must finish inside it. This is why etcd allows leader-local (lease) reads only with CheckQuorum on and says they rely on the clocks of all machines ([etcd raft README, Features](https://github.com/etcd-io/raft#features); the port refuses `ReadOnlyLeaseBased` without CheckQuorum, `raft.ts` line 91).
- **Not done: batch G**, the same bug at five times the load, which would show how fast the catch rate climbs with load. It waited 30 minutes for the shared lock behind other agents' timing runs and was cancelled to keep this experiment near its cost; `E46_BATCHES=G ./run.sh` runs it.

So the checkers catch what the history shows; whether a run shows a subtle bug depends on load and luck. Bug 1 is caught every time; bug 2 needs more load or more runs.

### Anomalies, each traced

1. **A reply after the test had ended** (c3-ri-s2, the only WARN in any run's log: [results/warnings.txt](results/warnings.txt)). Maelstrom asserted "Invalid dest" for a message from n0 to client c11, 54 ms after "Run complete". Traced ([results/anomalies/late-reply-c3-ri-s2.txt](results/anomalies/late-reply-c3-ri-s2.txt)): c11 sent a cas to n0 5 ms before a partition isolated n0; the client timed out after 1 s and recorded the cas as `info`; the entry had reached the log, and n0 applied it and answered ("from does not match") only after the final heal, when Maelstrom had already closed the client. The history is still right: `info` allows "did not happen". **Cause: harness timing. Not a bug.**
2. **More snapshots sent than restored** (batch C: 143 sent, 99 restored). Every MsgSnap was traced in Maelstrom's network journal ([results/anomalies/snapshot-audit.txt](results/anomalies/snapshot-audit.txt)): 1 was dropped by a partition (and sent again later); 42 receipts repeated a snapshot the follower had already restored; 1 arrived after the follower had already caught up by normal appends. Raft ignores the last two kinds, as it should, and every receipt was followed by the follower's accepted append response with an index at or past the snapshot. The repeats come from the wrapper: it reports each snapshot finished as soon as it sends it (Maelstrom has no delivery report), so raft probes the follower at once; a follower with a backlog (for example one just continued after a pause) rejects the probe, and the leader sends the snapshot again. **Cause: a wrapper choice; harmless. A real host should report a snapshot finished only when the follower has it, which saves the repeats.**
3. **Reads in only half the keys.** With `--concurrency 4n`, no key served by client threads 2n to 4n-1 ever got a read ([results/anomalies/reads-by-thread.txt](results/anomalies/reads-by-thread.txt)). Cause, read from the jar's own source: Jepsen's `independent/concurrent-generator` gives each key a group of 2n threads, and `gen/reserve` inside it hands reads to threads 0..n-1 by their absolute number, so the second group never reads (`jepsen/generator.clj`, `reserve`, whose own comment says "TODO: I think there might be a bug here ... an inner reserve might not understand that its threads don't start at 0"). Reads are also uneven across nodes: thread t talks to node t mod n (`jepsen/generator/interpreter.clj` line 89), and thread 0 gets most operations (c3-ri-s1: 779, 233 and 127 reads through n0, n1, n2). Every node still served reads, and every node both led and followed during a run (c3-ri-s1: n0, n1, n2 answered 514, 155 and 90 ReadIndex reads, and led in 5, 4 and 4 terms). **Cause: Maelstrom/Jepsen. Not fero's.** Batch F re-ran clean with `--concurrency 2n` (one group, so every key gets reads): all 4 runs valid in Knossos and Porcupine, every key had reads (4 to 9 keys per run, each with a longer history), and about 1,800 reads succeeded per run, twice as many as at 4n.
4. **Maelstrom 0.2.4 has no pause and no kill** (see Pauses). Worked around for pauses; kills not run.

Also seen and checked, not anomalies: many `no leader` refusals (up to a third of operations in a run; a node on the minority side refuses at once, which is correct) and the node counters in `summary.jsonl`'s `node_stats`, which come from the last 5-second STATS line and so trail the end of the run slightly (the table's snapshot counts come from the per-event log lines instead).

## What this box cannot show

- **Disk and crashes.** The log is in memory and no node crashes; Maelstrom 0.2.4 cannot kill or restart a node. So this says nothing about fsync order, torn writes, or a restart from a kept log. E-10's restart fuzz (1,000 scripts with crash-restarts, byte for byte against Go) is the evidence there; E-29 owns storage faults.
- **Real networks and clocks.** Maelstrom's network lives inside one JVM on one 4-vCPU box: no real TCP, no packet loss other than whole-link cuts, no one-way links, no clock skew. Lease-based reads (`ReadOnlyLeaseBased`), which depend on clocks, were not tested; every ReadIndex here is the safe kind. E-38 covers one-way and partial links in simulation.
- **Membership changes, leader transfer, async storage writes, many groups per process.** None are exercised: the voters are fixed, one group per process, synchronous storage. E-10's datadriven files and fuzz cover these inside one process; an end-to-end check of membership changes would need Maelstrom nodes that join and leave, which lin-kv does not do.
- **Speed.** Nothing here is a timing; the box was shared with other agents' heavy jobs during the runs. Latencies in Maelstrom's output are not quoted, and the checker durations above (Porcupine 0.5 s, Knossos over 18 minutes on one key) are wall times on that loaded box, not measurements.
- **Replay.** A Maelstrom run cannot be replayed exactly (no seed). The stores of every run are kept in `$SP/e46/runs/` for inspection; the trimmed results are here.
- **Checker strength.** Knossos checks each key's history on its own, and Maelstrom retires a key after 20 client processes have touched it, so each history stays small enough to check fully. A bug that only shows across keys (none is possible in a single-register store) would not be seen. With `--concurrency 4n` only half the keys had reads (anomaly 3), which batch F closes. The planted bugs show the checkers catch a stale read whenever the history holds one: always for bug 1; for bug 2 only in the runs where a write on the read key happened to finish inside the short window (1 of 4 at `--rate 50`). A bug that is wrong only in rare windows needs more load or many more runs than this. Knossos also has no time limit inside Maelstrom: on one 5-node key with 11 unknown-outcome operations it searched for over 18 minutes without an answer, where Porcupine needed 0.5 s.
