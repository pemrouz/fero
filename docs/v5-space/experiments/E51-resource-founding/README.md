# E-51: founding and finding a resource when each resource is its own cluster

**Question (Q-51).** With no `#meta`, do per-resource genesis, the home log's records and the soft directory keep one identity per resource and let clients find the right copy, and which of their rules are needed?

**Threshold** (set here: VERDICT 11.7 asks for the model, and names no threshold). Every stated property holds at every bound → the five records stand, at the counts the ablation gives. A counterexample in a design as written → the design text changes before the first build slice, and the record gains the rule that fixes it. A rule the ablation drops at every bound → the record loses it, or keeps it with what it really carries (speed, load, defence in depth) said plainly.

**In short.**

- **Yes, the design keeps one identity per resource and lets clients find the right copy, once five things in the text are fixed** (model-checked: eight small models, each in its own world, every property at every bound, up to 4,050,927 states for two resource names and two faults). With no `#meta`: one id per resource name (G1) and no copy holding another resource's id (ISO) hold through crashes, lost disks and cuts; a client never takes another project's or resource's copy for its own (D1); once calm, a client finds a live copy (FIND), the directory's table is rebuilt from announcements alone after its host moves (REBUILD), a connected client keeps working while every directory host is down (CONN), and the group records in the home log come to agree with the groups (REC). **Two limits on this yes.** The pieces are checked apart: no model runs founding and the directory together, and founding assumes every opener reaches the object store and the founder (skeptic F15). And G1 does not hold for a resource first founded on one box and later opened across boxes: E-33's `onebox1` counterexample (two ids, 3 steps) carries over once per resource, and needs E-33's rule per resource (below, "What the model leaves out"; docs and an experiment, E-33, not rerun here).
- **Five places where the design text is wrong or loose** (each a shortest trace, model-checked):
  1. **Founding: the opener must write its candidate id to disk before it asks the store to create it.** E-33 took the store create and the home group's first entry as one step. They are a store round trip and then a log write. If the opener holds the id only in memory, a plain crash between them (no lost disk) leaves the name stuck for good: the store holds the id, nobody holds it, every other opener adopts it and waits (G2, 6 steps). Writing the created id to disk when the create answers, this page's first fix, is not enough: a crash between the answer and the disk write strands the name the same way (6 steps; skeptic F1). The rule that holds: write a candidate id to disk, then ask the store to create that id; after the answer, or after a restart, compare the stored id with the candidate, and found only if they are equal, else drop the candidate and adopt the stored id. **Two new genesis rules**: the candidate on disk first (`cand.keep`, with `cand.noid`), and the compare (`first.mine`, `drop.other`, `drop.drop`).
  2. **"A client asks the directory only for a first address"** (V5-3, soft-directory rule 9) strands a client once every member it learned is dead or moved, while the directory lists a live copy (FIND, 5 steps). The "only once" half carries no stated property, only directory load: drop it, or keep it with a mark on members that failed since the last connection and ask again when all have failed (still retrying them: a version that forgot them broke CONN in a blackout, 10 steps).
  3. **A group's record write can be lost, and nothing writes it again** (REC, 5 steps; skeptic F2: the first version of this model never lost one). The write is a proposal to the home group's leader: it is lost if the group's leader dies after its config commits, or if the home leader changes before the record commits. The fix rewords rule 1: **a group's leader writes its record whenever the home log's record differs from the group's committed config** (it follows the home log anyway). It must keep comparing: a leader that writes again only until it has once seen its record shown breaks REC when rule 8's rewrite is lost too (9 steps). With rule 1 in this form, rule 1's write at each config change, rule 2 (an older config never overwrites a newer) and rule 8 (rewrite after the home group's recovery) have no counterexample at any bound.
  4. **The home group's own recovery has no second source.** After an operator recovery, old copies of a group learn the new incarnation from the home log or from a peer's HELLO. Both paths are needed: the home log for a data group whose recovered copy is down (5 steps), the HELLO for the home group (4 steps). The home group has only the HELLO. So while its recovered copy is down, an old home copy that comes back cannot learn the bump (INC, 5 steps), and once two old copies are back they can elect under the old incarnation (6 steps). In the model the window ends only when the recovered copy is back; in the design it also ends at the first HELLO from any member of the resource that has read the bump in the home log (reasoned: the model's HELLOs come only from the home group's own copies; skeptic F8). DESIGN-V5 accepts a residual window of two writers for a group cut off from the bump; for the home group it should say how this one ends.
  5. **The seed needs no mark.** A joining copy never applies its seed (DESIGN-V5 6.2, row 6), so only the founding entry applies one, once. The "applied once" check and the mark drop out (skeptic F9: the reason is the joiner, not the refusal of other options).
- **Counts** (DEV-10, against simplicity.json's reasoned counts; "record grain" counts simplicity.json's numbered rules, where a rule counts if any part of it is needed): genesis **14** rules (reasoned 4; at the record grain **6**: its 4, the candidate on disk first, and the compare); meta-catalog **7**, plus the high cross-key check (reasoned 5; at the record grain **4**: rule 4 has no needed part, since "the seed rides the founding entry" is genesis rule 2's first entry); meta-directory **10** (reasoned 8; at the record grain **6**: rule 1 reworded, 3, 4, 5, 6 and 7; rules 2 and 8 have no counterexample, and rule 6's settle.ms wait carries speed, reasoned; 7 if rule 2 is kept for configs that re-add a machine, reasoned); meta-members **2** (reasoned 2; this model has one guard at the add that serves as both rule 1's refusal and rule 2, and E-52's richer world, with learners and promotion, needs both: skeptic F3); soft-directory **17**, plus high rule 14 in v4's shape (reasoned 12; every one of its 12 rules has a needed part, rule 9 only its second half). Summed at the records' grain: **30** (29 with a directory host keyed to links), plus the two high rules where they apply, against 31 reasoned.
- **Not needed** at every bound (each dropped with no counterexample): the seed mark and a later opener's seed path (`first.mark`, `reseed.*`); "the old hash goes only after the new one is in" (covered by "only after the roll"); rule 1's write at each change and rules 2 and 8, once rule 1 is reworded; settle.ms before deleting a group's record (reasoned, not model-checked: this world has no client with a stale route, which is what the wait is for; skeptic F7); the directory's take-over and take-back checks on a server's own machine's directory; rule 9's "only a first address"; the leaver's directory exit and its never-re-announce (the refusal does their job, and once the leader's read of the directory can be stale they are no alternative to it: without the refusal P7 breaks in 5 steps; skeptic F4); and meta-members' high rule 3. E-33's `found.noid`, not needed there, is needed here: it moved to the candidate step, which reads no store (G2, 5 steps).
- **Outside the task's list:** this page makes no move on healing-self@per-resource. E-52 models healing per resource in a richer world and counts it (18 to 19, with `add.cand` needed twice). Here, dropping the leader's own link check (`add.live`) lets healing add a dead machine whose directory entry has not yet expired, remove it, and add it again: wasted config changes until the entry expires, not endless churn. That breaks this model's P9 limit of 6 changes (10 steps in the smallest model, 12 with every other rule in); at E-16's limit of 8 it holds with one crash and breaks with two (12 steps) (skeptic F16).
- DEV-10 mutants of the eight smallest models: **57 of 58 non-equivalent caught (98%)**; the one survivor is a stricter cross-key check that no stated property forbids.
- **How sure.** High for the traces and for the designs at these bounds (every reachable state explored). Medium for the counts: the worlds are small (up to four machines, two names, three faults) and separate; the greedy order decides which of two rules that cover each other is kept (here the reworded rule 1 over rule 1's commit-time write and rule 8); and the mapping to the record's rule numbers is this page's judgement. This version applies a skeptic's review (F1 to F16); every result was rerun from empty caches.

## Words used here

- **Resource**: a named, replicated table (`fero('orders')`). Here it is its own cluster (DECISIONS V5-2): its own Raft groups, its own settings, no project-wide `#meta`.
- **Home group**: the resource's first Raft group, founded at genesis. Its log, the **home log**, holds the resource's settings record, slot table and one record per group.
- **Genesis**: founding a resource on its first open. Here, as E-33's `objcas`: create the resource's **id** in the object store with **create-if-absent** (S3's `If-None-Match: *`); the opener whose create succeeds founds the home group as its only voter; every other opener **adopts** the stored id and joins as a copy.
- **Candidate**: the id an opener proposes for a new resource. It writes it to its own disk first, then asks the store to create it.
- **Settings record**: the first open's options (and later alters), the allowed **code hashes**, whether the **seed** (a `data:` start value) was applied, and the **write gate** (open, or read-only).
- **Group record**: a group's members and leader, in the home log, so a client can find the group (meta-directory@per-resource).
- **Incarnation**: a number an operator recovery raises, so old copies of a group can tell they are stale.
- **Soft directory** (V5-3): a lookup service that only helps clients find a first address. Servers **announce** what they hold; an entry lives only while its announcer's link lives; it keeps no log, and any machine can host it. **Seed directories** are the few a client knows.
- **HELLO**: the first message on a link; it names the project, the resource and the id.
- **Retiring**: a server that is leaving (Ctrl-C) and must get no new copies.
- **AG EF**: "from every reachable state, the goal can still be reached by calm steps", the liveness check of E-14, E-16 and E-33. **Calm steps**: protocol steps and timers, no faults and no recoveries.
- **DEV-10**: a **rule** is one guard conjunct or one state update; it counts only if dropping it lets the checker find a counterexample to a stated property at some bound. **Mutants** are made by script: drop each guard or update, flip each comparison, swap each pair of updates in one action.
- **Pinned**: a step of the world written as a rule (a Raft commit, a healing add, a fold), never dropped or mutated, so a vacuous model cannot pass (E-33's practice).
- **Probe**: a run of the design as the text first wrote it, or with one change, to show a counterexample; not a design.

## Method

Eight small exhaustive models in plain Python on E-16's engine ([../E16-controller-loop/engine/engine.py](../E16-controller-loop/engine/engine.py)), which imports E-17's rule language ([../E17-partitioning/harness/dsl.py](../E17-partitioning/harness/dsl.py)) unchanged. The ablation and the mutants are E-17's procedure as E-16 extended it: pass 1 (drop each rule alone), greedy drops in model-text order, a final pass that proves the set left 1-minimal, a verify pass 1 and the verify bound, then the mutants of the smallest model, with a mutant judged equivalent when its reachable state set is the same. Each run is breadth first over every reachable state, so every trace is a shortest one.

Each model brings its own small world, as E-16 and E-33 did. So how the pieces work together is not checked: founding runs with no directory, and the directory with no founding (skeptic F15). One big world with every piece would not finish on this box (a two-seed directory world alone is 170,709 states before any rule is dropped).

The split follows the records. Each rule in a model names its record in its `role` (`genesis`, `catalog`, `records`, `members`, `softdir`), and the tables below map each to the record's rule number in [simplicity.json](../../judging/simplicity.json).

The properties, in words (each model's docstring has the exact text):

- **G1**, one id per resource: never two ids minted for one name that each have a committed client write and a copy still holding them (E-33's G1, per resource).
- **ISO**, isolation: a machine's dir for name r holds only an id minted for r.
- **CAT1**: every copy of a resource runs the first open's options. **CAT3**: every copy runs a code hash the settings allow.
- **SEED**: a resource's seed is applied at most once, and never after a client write (it would overwrite it).
- **G2** (AG EF), founding completes: where the home group has a live majority, calm steps reach a working home group with every live opener whose options match as a copy, and the seed applied. A stored id whose holders lost their disks is F-12 and not judged.
- **D1**: a client never treats another project's copy, or a server that holds no copy of the resource, as its own (soft-directory rule 8's property).
- **FIND** (AG EF): once calm, a client finds a live copy of a resource that has one (dirtable: some reachable seed lists one; client: the client is connected to one).
- **CONN** (AG EF, V5-3): a client that was connected keeps working while every directory host is down for good, as long as a member the resource told it of is alive.
- **REC** (AG EF): the group records in the home log agree with what the groups hold.
- **REBUILD** (AG EF): after a directory host moves (or anything else), every seed directory's table holds exactly the live copies it reaches, rebuilt from announcements alone.
- **INC** (AG EF): after an operator recovery, every old copy stops and comes back as a new copy; only the recovered copy serves. "Serves" in the model means "is up and has not stopped": the model has no elections, so one old copy alone cannot lead.
- **DUR**: no copy deletes the log of a group it is still a voter of. **SLOT**: the slot table never points at a deleted group. **HIST**: a deleted group's history is in the tier.
- **P3**: at most one extra copy (E-16's P3). **P7**: no copy is added on a retiring machine (healing.py round 2's P7, which E-16 could not ask). **P9**: no more than 6 config changes without an outside event (E-16 allows 8). **HEAL**, **LEAVE** (AG EF): healing finishes; a leave ends with no copy on the leaver.
- **AVAIL**: no alter or roll step takes the majority away ("online"). **GATE**: no write commits in a group that has applied the read-only gate. **KEYS**: the settings keep standbys at or above copies. **ROLL** (AG EF): a code roll finishes.

Bounds are in each model (`BOUNDS`, `SWEEP`, `VERIFY`); the results name the bound of each counterexample.

### 2. Where the design text is wrong or loose

**Founding needs the candidate on disk before the create** ([results/probes.txt](results/probes.txt), `found.py objcas-mem` and `objcas-after`, G2, 6 steps each). Machines 0, 1 and 2 start; machine 0 picks a candidate id; its create of resource r's id succeeds in the store; machine 0 crashes before it writes the home group's first entry. In `objcas-mem` it held the id only in memory. In `objcas-after` it would have written the id to disk once the create answered, the fix this page first proposed, and the crash falls between the answer and the disk write. Either way the store holds the id, no machine holds it, and every opener (machine 0 too, once back) adopts it and waits for a home group that will never exist. No disk was lost, so this is not F-12. E-33's model took the create and the first entry as one step and could not see it. The first version of this page made the same merge: it wrote the created id to disk in the same step as the create, which no builder can do (skeptic F1). The design now writes the candidate to disk first (`cand.keep`), creates it (`put`), and compares: an opener founds only if the stored id is its candidate (`first.mine`), and drops a candidate that lost (`drop.other`, `drop.drop`) to adopt the stored id. A lost disk in that gap is F-12 (the founder is the only voter until two others join, as in E-33; the operator clears or restores the name) and is not judged.

**A client that asks only once** ([results/probes.txt](results/probes.txt), `client.py --drop dialfail.mark`, FIND, 5 steps). Machine 0 crashes; the client looks the resource up, connects to machine 1 and is told the members {0, 1}; healing moves machine 1's copy to machine 2. The client loses its copy, redials machine 0 (down) and machine 1 (no copy any more), and, since it "asks the directory only for a first address", never asks again, though the directory lists machine 2. The ablation drops rule 9's "only once" half (`lookup.first`) as needed by nothing stated: it saves directory load. A design that keeps it needs the client to mark members that failed since its last connection and ask the directory when all have (`dialfail.mark`); an earlier version of this model that forgot a failed member instead broke CONN in 10 steps (in a blackout, the member came back and the client no longer knew it; that version is not kept).

**A lost record write** ([results/probes.txt](results/probes.txt), `records.py noresend`, REC, 5 steps on `e2`, 3 on `m2`). G's config moves to epoch 1, then 2; the write of epoch 2's record is lost (G's leader died after the commit, or H's leader changed before the record committed). The home log names epoch 1 for good: nothing in rules 1 to 8 writes it again, and a removed copy waits for good to delete its data (rule 5). The first version of this model never lost a record write, and every rule then held REC (skeptic F2). The design now writes the record whenever the home log's record differs from G's committed config (`resend.again`). It must keep comparing for good: the `ack` probe, which writes again only until the record has once been shown, breaks REC on `e2m2` in 9 steps (the record is shown, H is recovered from a copy that was behind, rule 8's rewrite is lost, and nothing writes again).

**The home group's recovery** (`incarnation.py --bound home3s`, INC, 5 steps; `home3e`, 6 steps). Copies 1 and 2 of the home group crash; the operator recovers it on copy 0; copy 0 crashes; copy 1 comes back. It holds the old home and has nothing to learn the bump from: the home group has no other log, and the only copy whose HELLO carries the new incarnation is down. One old copy cannot lead; with a sixth step, copy 2 back too, two old copies are up, a majority of the old three, and they can elect under the old incarnation (`home3e`: INC judged only there, and stuck). For a data group the same states are safe, because its old copies read the bump in the home log (`data3e` holds; `logstop` is needed: 5 steps). So rule 4's two paths are both needed, one for each kind of group, and the home group's recovery leaves a window. In the model it ends only when the recovered copy is back. In the design it also ends at the first HELLO from any member of the resource that has read the bump in the home log, if the HELLO carries the home group's incarnation (reasoned; skeptic F8). INC is judged for the home group only while the recovered copy is up.

**The seed.** The ablation drops the seed mark and the later opener's seed path together (`first.mark`, `reseed.*`). The reason is the join: with no `reseed` step, a copy that joins never applies a seed, so the founding entry is the only place one is applied, once (DESIGN-V5 6.2, row 6: "a joining copy skips its seed"). Each was needed alone while the other existed (SEED, 5 steps), which is why the minimal model has neither. The first version of this page gave another reason, that an open with other options is refused (`join.same`); that is not what the model shows, since `reseed` acts on copies that have already joined with the same options (skeptic F9).

- `cand.keep` breaks G2 in 2 steps because without it no opener has a candidate, so nothing is ever founded. The crash cases are the probes of section 2 (6 steps).
- `cand.noid` is E-33's `found.noid` moved to the candidate step. E-33 did not need it, since its create also checked the store; the candidate step reads no store. Without it, an opener whose candidate the store already took writes a new candidate over it before its first entry, and the name is stranded (G2, 5 steps).
- `first.mine`: without the compare, two openers each found a home group on their own candidate and each takes a write (G1, 8 steps). `drop.other`: without it the founder drops its own stored candidate (G2, 5 steps).
- `adopt.noid`: without it the founder re-adopts its own stored id and its copy becomes "known", so the home group loses its only voter (5 steps). This is because the model's adopt writes "known" over whatever the dir holds; E-33's adopt kept a copy's state, so the guard was not needed there. It is needed here because of how the update is written, not because E-33 missed it; the record's grain is not affected (skeptic F10).
- `adopt.key`: an opener of resource r1 reads the id stored under r0's key (ISO, 3 steps): the key must carry the project and the name. The project part is the same comparison (reasoned).
- `alteradd.entry` and `alterrm.entry` are the alter itself (ROLL never finishes without them); `write.gate` and `alterkey.consistent` are judged by properties that are their own words (GATE, KEYS): the models show only that nothing else enforces them.
- `resend.again` is the only rule that writes a record in the smallest model: once a leader writes whenever the home log's record differs from its committed config, rule 1's write at each change (`commit.record`) and rule 8's rewrite after H's recovery (`rewrite.again`) are covered, and so is rule 2 (`setrec.newer`): an older record that lands late is written over again. Rule 2 still keeps the home log from going back for a while, and rule 5's garbage collection reads the record; in this world no config re-adds a machine it removed, so a stale record never tells a voter to delete its data (reasoned, not modelled). The page keeps rule 2 out of the model-checked count and says so.
- `rconnect.take` and `expire.owner` are rule 11's two halves on a link to another machine's seed: a server cut off and back opens a new link while the directory still holds the old one; without the take-over its re-announcement leaves the entries owned by the old link (REBUILD, 6 steps), and without the owner check the old link's death drops an entry the new link now owns (7 steps). On a server's own machine's directory, and for take-backs, the halves are not needed here: in these worlds a machine's server and its directory host die together, and an address holds one process. v4 keeps them for a wedged process whose successor reuses its identity (code: api/directory.ts:272 for the take-over, :293 for the take-back; reasoned, not modelled).
- `rconnect.open`'s 0-step trace on `r1` (one seed) shows only that a server must link to a seed on another machine at all; "every seed" is held only by REBUILD's wording on `d2` (see "What the model leaves out"; skeptic F14).

Both exist because v4's host learns who is up from its published peer table. `dirtable.py`'s host keys entries to the link itself and needs neither: REBUILD holds there with no seen mark and no grace (model-checked at its bounds).
- `add.live` (healing-self's high rule, E-52's record): a machine entry outlives a dead machine until the failure detector drops it. Without the leader's own link check, healing adds the dead machine, removes it, and adds it again while the entry lives. That is wasted config changes until the entry expires, not endless churn: the model lets the expiry wait, so P9 counts the changes made meanwhile. At this model's limit of 6 changes it breaks P9 on `p1` (10 steps; 12 with every other rule in); at E-16's limit of 8, `p1` holds and `p2` (two crashes) breaks in 12 steps (skeptic F16). In real healing a removal also waits `evict.after` (E-16's `remove.gone`, pinned out here), so the waste is smaller still (reasoned). E-52 finds `add.cand` needed twice in its richer world.
- meta-members: the ablation keeps {the mark, the refusal at the add}, with the leader reading the live table in the add step and also with stale reads (`stale`: the same five rules kept, 5 of 5 mutants caught). The first version said {the mark, the directory exit, never re-announce} was another minimal set. That holds only because the leader's read and its add were one step: with a stale read, dropping the refusal breaks P7 in 5 steps on every bound (crash 0; machine 2 announces itself; the leader reads the directory; machine 2 starts its leave; the leader adds machine 2). So the refusal is the only minimal set once reads can be stale, and the directory exit only saves wasted picks (skeptic F4).
- meta-members' count: this model's one guard at the add (`add.refuse`) stands for both rule 1's refusal and rule 2 ("healing never adds it"). E-52, with learners and promotion, needs both a check at the add and one at the promotion (P7 in 2 and 6 steps), and counts the record at 2. So does this page (skeptic F3).

### 6. What was fixed in the models on the way

Each model's first version had a slip in its world, which a run exposed before any ablation; each is fixed in the files here, and each is a world step, not a counted rule:

- found: a joiner added straight as a voter left a two-voter group that one crash stopped; DESIGN-V5 grows from one voter to three (a learner first). G2 also first excluded any stored id with no holder as F-12, which hid the founding probe; now only ids whose holder lost a disk are excluded.
- dirtable: a new link could reuse the identity of a closed link whose entries were still waiting to expire, and healing a cut did not break links that now crossed sides.
- client: see section 2 (the failed-member mark).
- place: a crashed retiring machine was never replaced, the leave's one add could be used up by healing's own removal, and growth back to the target after a leave was missing. P7 first read the retiring flag that `leave.mark` sets, so dropping that rule made P7 empty and the first ablation dropped every meta-members rule; a ghost now records who is leaving.
- incarnation: INC first leaned on the raised number itself, which hid `recover.raise`; it now says "only the recovered copy serves".
- records: tiering only after a slot move made `delete.noslots` look covered; the tier now runs at any time, and the slot can move back.
- catalog: a write that changed no state never formed an edge, so GATE could not be judged; a ghost marks it.
- fold: two link events inside one fold window broke REBUILD in the design; v4 runs its fold as a microtask before the next socket event, so the model now does too.

After a skeptic's review of the first version (findings F1 to F16), these changed, and every result above was rerun from empty caches:

- found (F1): founding is now a candidate on disk, the create, then the compare; the first version wrote the created id to disk in the same step as the create. Probes `objcas-mem` and `objcas-after` show both earlier forms failing.
- records (F2): a record write can now be lost (a fault), and rule 1 is reworded to write again while the home log's record differs; probes `noresend` and `ack`.
- place (F4, F16): the `stale` option (the leader's read of the directory is its own step) and a `churn` bound setting, to run P9 at E-16's 8.
- incarnation (F8): the `home3e` and `data3e` probes (two old copies up, the recovered copy down).
- fold (F11): GRACE = 3, as in v4 (api/directory.ts:199); the first version had 2. Same states and traces.
- run.sh (F12, F13): caches keyed to a hash of the model text; the "STOPPED AT THE STATE LIMIT" label explained; found's design bounds run with a state limit of 8,000,000.

## What the model leaves out

- **Leaders, elections and V5-7's hand-back** are in no model here (skeptic F6). Raft is abstract in every model: a group commits while a majority of its voters are up, linked and hold a copy; elections, catch-up and config changes are atomic steps. E-14, E-14b, E-14c and E-46 check Raft itself; E-52 models the hand-back's rules and E-53 its pace. So REC checks only a record's config, never its leader. Rule 1 writes the record when the config differs, so after an election or a hand-back the record's leader is stale. That is safe if the leader field is a hint: a client that dials a stale leader is answered `moved`, which names the current one (docs: DESIGN-V5.md:561, "A stale answer costs one `moved`"), so a stale leader costs one round trip (reasoned). If the record's leader must be exact, a write on every leader change is one more rule, which this page does not count.
- **Healing is pinned** (E-16's `self` rules), except the guards this experiment counts (the candidate's code, the retiring checks, the leader's own link). Growth from one voter to three is one atomic step (DESIGN-V5 4.2: never two voters). E-52 models healing per resource in a richer world.
- **Small, separate worlds.** Three machines (four in `place.py`), one or two resource names, one data group, up to three faults. The client model has one client and one resource; the table model one or two seed directories. No model runs founding and the directory together: G2 assumes every opener reaches the store and the founder, and no property checks finding a resource while it is being founded, or during a blackout (skeptic F15).
- **FIND asks only that some seed lists a copy.** Every sweep bound has one seed directory; only `d2` (a verify bound) has two. So soft-directory rule 7's "to every seed" is held only by REBUILD's own wording on `d2` (every seed's table holds every copy it reaches). Its 0-step trace on `r1` shows only that a server must link to a seed on another machine at all. That a client that asks one seed needs "every" is reasoned, not model-checked (skeptic F14).
- **No client with a stale route in the records world** (skeptic F7). settle.ms exists for that client: until a deleted group's record goes, its former members answer `moved` from the table (docs: DESIGN-V5.md:507). With no such client, dropping the wait cannot break anything here, so "settle.ms is not needed" is reasoned: a client with a stale route falls back to the resource or to the directory and asks again (soft-directory rule 10), so the wait carries speed.
- **No config re-adds a machine it removed** in the records world. So with rule 2 dropped, a late old record never tells a re-added voter that it is removed. Rule 5's garbage collection reads the record, and with re-adds an older record could tell a voter to delete its data (reasoned, not modelled).
- **The home group's HELLO peers** are only its own copies. In the design, any member of the resource that has read the bump in the home log could carry it in its HELLO (reasoned; skeptic F8).
- **The object store is always reachable and its create-if-absent is atomic** (E-28 measured MinIO's conditional PUT; TOOLS.md's smoke test answered 200 then 412). A store outage at a first open delays founding. A candidate id is unique (a random id); the model numbers it when the store takes it.
- **The one-box path** (genesis high 9: a resource founded on one box with no object store, by an exclusive file create) is not modelled again (skeptic F5). E-33's one-box model counted 4 rules plus the exclusive create. Its `onebox1` bound carries over per resource: if one box holds an id for a name from a one-box run, with writes, and other boxes then found that name through the object store, there are two ids, both with writes (G1, 3 steps under create-if-absent; experiment E-33). This page does not rerun it, and its G1 holds only without it. E-33's rule, per resource: the other boxes join a resource that holds a one-box id and never found it themselves (or, reasoned, the one-box id is first put in the store by create-if-absent, so the others adopt it). That rule belongs to genesis high 9's one-box path.
- **No resource delete.** So a same-name resource with a new id never exists, and the HELLO's id check (soft-directory rule 8's third part) is not exercised. A first lookup could not tell an old id from a new one from the HELLO alone (reasoned): the design text says nothing on deleting a resource, and needs to before delete is built.
- **No loopback addresses** (soft-directory high rule 13): with rule 8 in place, a loopback address from another machine can only cost a failed dial, never a wrong copy (reasoned), so it carries speed, not a stated property.
- **v4's fold race** is modelled as one pending fold that runs before the host handles the next link event (v4's `afterFold` microtask); a register may beat its own link's fold.
- **cluster-version, cluster-credentials, planner-hints and healing-self's rule 15** (the stored placement) are not in this task's list and are not modelled here.
- **Liveness is "a path exists"** (AG EF), not a fairness proof. Control steps (the operator's alters, a roll) count as calm only in `catalog.py`, as E-33's `init` counted the operator. A `time` step (an entry expiring) can wait for ever, so P9 counts the changes made while it waits.

## Against the threshold

The threshold (set here): every stated property holds at every bound → the five records stand at the counts the ablation gives; a counterexample in a design as written → the text changes before the first build slice and the record gains the fixing rule; a rule dropped at every bound → the record loses it, or keeps it with what it really carries.

- **Every stated property holds at every bound** with the designs as modelled (section 1). The question's answer is yes: with no `#meta`, per-resource genesis keeps one id per resource name (G1) and resources apart (ISO), the home log's records come to agree with the groups (REC), also when a record write is lost and when the home group is recovered from a copy that was behind, and the soft directory lets a client find the right copy (D1, FIND), rebuilds itself from announcements alone (REBUILD), and is not needed by a connected client (CONN). Two limits: the worlds are separate, and G1 does not cover a resource first founded on one box (E-33's carry-over, per resource; not rerun here).
- **Counterexamples in the design as written: five** (section 2). Founding needs the candidate on disk before the create and a compare after it (+2 genesis rules); rule 9's "asks only once" strands a client (drop it, or add the failed-member mark); a lost record write is never redone (rule 1 reworded, which also covers rules 2 and 8 here); the home group's recovery leaves a window the text should state; the seed needs no mark. None needs a new mechanism.
- **Rules dropped at every bound** (section 3): the seed mark and a later opener's seed path, rule 2's "after the new one is in", rule 1's commit-time write and rules 2 and 8 once rule 1 is reworded, settle.ms before deleting a group's record (reasoned: this world has no client with a stale route), rule 9's "only once", rule 11's halves on a server's own machine and on take-back, the leaver's directory exit and never-re-announce, and meta-members' high rule 3. Each is either covered by a rule kept or carries only speed or load, except rule 2, which may carry safety where a config can re-add a machine (reasoned, not modelled): the record should say which.
- **Counts:** at the records' grain the five sum to 30, against the reasoned 31 (genesis +2, meta-catalog −1, meta-directory −2; 31 if rule 2 is kept); at DEV-10's grain 50, plus two high rules that are needed where they apply (the cross-key check; v4's grace). healing-self@per-resource is E-52's to count.
