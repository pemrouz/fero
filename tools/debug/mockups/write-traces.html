Data sources — how this write trace is assembled

The change record (centre). The committed write's own {type, key, value, origin, seq, epoch} ChangeRecord — the wire format itself [C]. The client stamp, the owner restamp (the value's origin is replaced by the owner at commitLocal), and the winner stamp are real ProvRecord fields.

Outcome (local / won / forwarded / dropped·dedup / lost·fence / lost·conflict). The record's own commit classification from the __observe stream's local / won / forwarded / lost events [B]. A lost event carries the winning epoch/seq as we/ws; compared against the lost write's own wr.e: wr.e == we ⇒ same-epoch conflict; wr.e < we ⇒ fence (stale-view write rejected — DECISIONS X).

The route — one row across nodes ⚠ NEW. Stitching the hops client → forwarder → owner → replicas into ONE write needs a client-stamped correlation id carried WRITE → owner commit → replication → won/lost emits. The hops themselves are real (transport WRITE/ACK, commitLocal restamp, RECORDS fan-out), but joining them on one identity is proposed instrumentation.

Ack roster & W-quorum. Which replicas acknowledged the commit + their lag comes from the snapshot marks/heads vs the floor [A]; the per-write WRITE→ACK match (forward confirmed / timed out) is the same ⚠ NEW correlation id. The confirm threshold (W-quorum on the async storage seam) is real (DECISIONS — confirm:'persisted').
