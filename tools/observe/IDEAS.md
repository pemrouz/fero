Open ideas for the fero-v2 network observer & dashboard, beyond the shipped scope. Each

up starts from a known anchor. Graduate landed items to the repo-root [DECISIONS.md](../../DECISIONS.md);

## Shipped so far
- **[a] topology** — peer grid + epoch/writable gate + convergence pill (Slice 1).
- **[a] DHT ownership ring** — per-card conic-gradient keyspace donut, scale-independent `coverage(k)` sampling (Slice 2).
- **[b] live data + provenance stream** — gated `__observe` push-hook → bounded ring-buffer ViewProxy → bridge (batched, drop-oldest, `by`-attributed SSE) → dashboard provenance ticker + hot-keys table + per-kind stat chips (Slice 3).
- **[c] replication health** — two panels built ENTIRELY from the already-polled `__inspect` snapshot (`marks`/`log.size`/`orphans`), zero new server instrumentation: a **catch-up leaderboard** (per-node lag, CSS-`order`-sorted worst-first, bars drain as nodes reach the frontier) + a **log-growth sparkline** (cluster-total retained records over time — the uncompacted-log signal; flattens once compaction lands) + a calm orphans line.
  - **Non-obvious metric choice (floor-relative lag):** a node's "behind" is measured vs the **most-caught-up node** (the floor), NOT the absolute frontier. A replica always trails its owner by the in-flight pipeline depth; summed across partitions that's hundreds of records, roughly UNIFORM across nodes, and healthy — so absolute lag reads scary-but-meaningless and never goes calm. Floor-relative reads "caught up" when the cluster trails uniformly and reserves the bars for a genuine OUTLIER (a draining rejoin / a stuck node). **Blind spot (accepted):** a GLOBAL replication stall (everyone trailing the owners together) shows as excess≈0 here — it surfaces instead in the log-growth sparkline climbing + replication/s dropping. *Hook:* the per-second `setInterval` in `web/app.js` over `model.nodes`.
  - **Second metric choice (dead-origin exclusion) — "thousands behind" INVESTIGATED.** A long-churned cluster surfaced nodes "tens-of-thousands behind & climbing". Controlled investigation (single + 10× kill/restart cycles, measured from `[diagnostics].snapshot`): a clean restart reconverges in **~2s** and drains to 0; membership ALWAYS reconverges fast (≤5s) even at cycle 10. The big numbers are NOT a stuck node or a convergence failure — they are (a) the **no-compaction tax**: every kill+restart mints a NEW origin uuid (10 cycles → 6→15 distinct origins) and the log never compacts (1k→2.7k→…→100k+), so a rejoiner must replay a bloated history; and (b) **dashboard over-reading**: the frontier counted DEAD-origin debris (those retired uuids) as live "behind". Fix: compute the frontier/lag over **live origins only** (`origin` of a `seenKey` must be a current live-member uuid) — catch-up then measures only LIVE-traffic deficit (drains in seconds, calm in steady state) while the dead-origin bloat shows where it belongs, the **log-growth sparkline**. The residual rejoin SPIKE that remains is real and **proportional to log size** — it shrinks once compaction lands (the panel becomes the before/after proof). *Hook:* `isLiveOrigin` in the `web/app.js` replication tick; ties to the fero-side **log compaction / epoch-aware catch-up** item above.

- **convergence timeline** — the HISTORY behind the topbar pill: a drop-oldest ring (150×1s ≈ 2½ min) sampled from `model.nodes`, rendered as a state band (one tick/sample, CSS-`order` time layout over stable DOM keys) + a fixed 0–100% writable-fraction (availability) sparkline + a "converged · 4m12s" stability/MTTR headline + a **scrub** (one delegated band listener: hover previews a moment's state in the header, click PINS it, click-again unpins). Browser-only (the bridge-buffered version is the scale tier). Full per-node time-travel (rewind the whole dashboard, not just the convergence summary) stays the separate "Log replay scrubber" backlog item. Turns the instantaneous "are we converged?" into "when did it diverge, how long, what shape was the heal".
  - **Non-obvious classification (3-state, writable-MAJORITY partition).** The pill+band share ONE debounced state. RED `partition` is reserved for **≥2 writable MAJORITIES** (genuine split-brain), NOT any 2 writable views. Verified in the harness ([investigate-views](/tmp) — reproduced below for the record): a kill+restart makes the rejoiner boot **solo-writable** (`e1/members=[self]/W`) for ~3s before it joins, so a naive "≥2 writable views" (and even the plan's literal "majority of own member set") wrongly flags every rejoin as split-brain. Fix: a partition SIDE must be writable AND a majority of the cluster (`size > maxViewSize/2`); a lone pre-join node or a minority that correctly went read-only is the healthy `converging` (amber). Plus a **persistence debounce** (raw dual-majority must hold ≥3 samples before escalating to red) as a second layer. *Hook:* `convergence()` + the timeline `setInterval` in `web/app.js`.

- **scale tier (war-game views)** — at >`aggregateAbove` (default 24) server nodes the bridge STOPS the per-node `snapshot` fan-out (the O(N²)/poll wall) and ships ONLY a compact `aggregate` rollup (an exported pure `deriveAggregate(snapshots,mode,suppressed)` — view-groups + 3-state convergence + cluster totals + top-K lag, all O(groups+topK)); the dashboard switches the per-node grid to **view-group BLOBS** (one circle per committed view, sized by node count — a partition = ≥2 blobs; singletons fold into an `others` blob), drives convergence/pill/timeline/counts + the catch-up leaderboard from the rollup, and gates the prune loop off (un-sampled nodes must NOT self-evict). The mode is hysteretic (first tick decides; later flips debounce 3 ticks). `dropped:{snapshots,mode}` ships every rollup — **no silent loss** ("aggregated at scale (N nodes)"). Validated with a SYNTHETIC source (`bridge.test.ts`: converged→1 group, 30/20 split-brain→2 writable-majority groups→partition, clean-minority-read-only→converging + singleton fold, top-K ranking) + a perf guard (`bridge.perf.ts`: deriveAggregate over 200 dead-origin-laden snapshots, **4.9ms** median < 8ms — an order-independent memoized view-hash replaced the O(N²) member-join).
  - **Validation ceiling (measured):** in-process forms cleanly to **n≤50** (~4.3s); **n=100 never forms** (discovery cliff, all nodes solo) and **n=200 is rejected** (0/199 sockets). At n=50 the in-process bridge HTTP is **event-loop-starved** during partition/churn (the plan's risk — the poll competes with consensus); a lighter **n=40** config (slower heartbeat, lower writes, poll 1500ms) keeps the dashboard responsive. The aggregation is source-agnostic over InspectSnapshot, so N=200+ rides a real multi-process cluster (network source) or the synthetic source — NOT the in-process harness. **Also found:** in-process `partition()` severs DATA but not the failure-detector, so a split only becomes a *membership* split (→ 2 blobs) with fast `evictAfter`; otherwise it's a silent write-gate.
  - **Bug fixed in-flight:** the writable-MAJORITY split-brain rule must compare a group's REPS to its OWN member count (`size≥2 && reps>size/2`), NOT `size>maxGroupSize/2` — the latter falsely flagged a healthy transition as "2 writable majorities". Fixed in BOTH `convergence()` (web/app.js) and `deriveAggregate` (bridge.ts) so blobs/grid agree.

- **scale tier · Stage C (key-movement heatmap + provenance rollup)** — the two remaining war-game views from plan §3.5, both bridge-side fan-in + browser render, **no new server instrumentation**:
  - **Key-movement heatmap** — `deriveAggregate` now ships `cover`: the consensus ownership donut. `ring.coverage[i]` is a member-INDEX into THAT node's `ring.members`, meaningless across nodes/ticks — so the bridge resolves it to the owner ADDRESS (`coverFrom`) of the **largest view-group's** ring (the authoritative one; during a partition the majority side's ownership is what's live, the minority is read-only). The dashboard (`updateHeat`) diffs successive `cover` arrays: a segment whose owner changed FLASHES (heat→1, white overlay) then decays ×0.5/tick (~3s tail), so a rebalance reads as a **wave across the keyspace that settles** — the spatial complement to the [c] orphan line. Cells are FIXED slots `0..K-1` (never deleted → no keyed-list churn); `cover` is O(segments), shipped in BOTH modes so the strip works at every scale (at war-game scale it replaces the unreadable 40k-vnode arcs). The first `cover` is skipped (else every segment reads as "moved").
  - **Provenance rollup** — at scale the raw per-record `records` firehose can't reach the browser (O(writes); a heal floods it), so in blobs mode the bridge REDUCES the `__observe` stream it already receives into a compact `provagg` per 1s window — per-second write/repl rates, **windowed** conflict/rebalance counts, top-K hot keys + top-K hot **origins** (busiest writers) — and SUPPRESSES the raw fan-out (`pushEvent` only buffers `events` when `aggMode==='grid'`; the rollup accumulators are O(1)/event, reset each window). Grid mode keeps the raw `onEvent()` drill-down. The dashboard drives the SAME activity rates (one binding, both modes) + a writes/s sparkline + blobs-only hot-keys/origins boards from `provagg`; the grid per-second rate interval is gated off in blobs mode so the two sources never fight. The conflict-vs-rebalance split (same-epoch loser = TRUE conflict; epoch-fenced = expected churn) is computed identically bridge-side and client-side. `provagg.nodes` reports how many node-streams the rollup folds (honest: it's an aggregate, not one node).
  - **Validated** (`bridge.test.ts`): `cover` resolves member-index→address; `cover` follows the MAJORITY view during a partition + maps unowned (`-1`) → `''`; `provagg` ships rates + top-K keys/origins AND the raw `records` firehose is suppressed in blobs mode (`recs.length===0`). Perf guard extended — `bridge.perf.ts` now fabricates a full 120-segment coverage so the `cover` resolution is measured; deriveAggregate **~4.5ms** median < 8ms (cover adds ~0.5ms — negligible vs the ~40k-iteration frontier/lag loops that dominate; the threshold was NOT widened). Hardened the flaky observe-stream test to wait for the SPECIFIC write keys, not a raw event count (keyless formation events satisfied it prematurely).
  - **Adversarial review (4-dimension workflow) → 7 findings, all fixed:** (1) durable perf headroom — `lagOf` now iterates DENSE frontier arrays once, not a `for (k in frontier)` object-enumeration N times (the apparent "50% flake" was contention, not the code — but the optimization is the rule-compliant response, threshold untouched); (2) no steady-state allocation in blobs mode — `account()` reads scalars off the raw record and only materializes the flattened `{…e,by}` event in grid mode (the only path that retains it); (3) `flushEvents` is mode-gated so a grid→blobs flip can't leak a stale raw batch into a blobs dashboard; (4) `ingestProvAgg` sets `aggMode='blobs'` so the grid rate interval gates off the instant a rollup arrives (no 1-tick rate fight); (5) **honest labels** — the "top origins" board is `origin`=the COMMITTING node (a forwarded write is restamped `origin=owner` at commit, [resource/index.ts:735](../../resource/index.ts)), so it's relabeled "**busiest owners** · most writes committed (by sequencer)", NOT "busiest writers"; (6) the consensus-`cover` lead tiebreak is now epoch-aware (freshest view wins a reps tie → no phantom rebalance wave at a view-install boundary); (7) defensive heatmap reconcile-down (inert today at fixed `RING_SEGMENTS=120`, but a shorter cover would otherwise freeze orphaned cells).
  - **Open (Stage C follow-ups):** (1) the `network` source still subscribes `__observe` on ALL N nodes — the firehose INTO the bridge is unbounded there (in-process/harness it's free function calls); §3.5(c)'s "**selective/sampled `__observe` subscribe at scale**" (sample K-of-N, label the rollup as sampled) is the remaining axis. (2) Membership/conflict **notable-events log at scale** (aggregated, not a per-event firehose) — currently grid-only; the timeline+blobs carry the membership story and `conflicts/s` the alarm, but a folded notable feed is a future panel. *Hook:* the `prov` accumulators in `bridge.ts` + a sampling cap in `ensureObserve`.

- **operational polish — alerts strip + freeze (browser-only).** The "small polish" pass, scoped by purpose (two affordances built, two consciously dropped — see UI affordances):
  - **Alerts strip** — the operational LAYER over the panels: a FIXED set of active, actionable alarms with how long each has held, derived (no new data) in the 1 Hz timeline sampler from already-computed signals — **partition** (crit; the DEBOUNCED state, so a rejoin blip never raises it), **quorum lost** (crit; writable-fraction 0), **catch-up stalled** (warn; total-behind that PERSISTS > 8 s — a healthy rejoin drains faster), **conflicts** (warn; same-epoch losers in the 5 s window). ## Surfaced while building the dashboard
- **`data` keyed-list orphans on delete+re-add** — deleting a key from a `$()` proxy that backs a
  `render` keyed list, then re-adding the SAME key, leaves the old (blank) `<li>` orphaned in the DOM
  (model stays correct, DOM count grows unbounded). Worked around in the hot-keys panel with **stable
  slot keys** ('0'..'39') whose values update in place (the displayed key is a field, never a model key),
  so the keyed list never churns keys. Worth a fix/repro upstream in `data`.
- **Node failure → a burst of LWW losers under scoped R<N — INVESTIGATED.** A node kill+restart surfaced
  hundreds of `lost` events. Root cause, nailed by a controlled aging experiment (categorising every loser
  by winner stamp `we`/`ws`):
  - **100% are epoch-fence** (loser's view epoch < winner's) — zero same-epoch/seq contention. So it is the
    epoch-fencing mechanism (DECISIONS V1d) working AS DESIGNED; the data converges correctly, nothing is
    lost beyond LWW semantics. NOT a bug.
  - **They scale with the LOG SIZE / re-write rate.** Unique-key workload (nothing to supersede) → ~0
    losers even over 10 rejoin cycles; re-writing the same keys → 400+ and growing with each cycle as the
    log grows (the log never compacts). On rejoin, anti-entropy re-delivers historical SUPERSEDED versions
    (the seq-based digest is epoch-unaware), and each old-epoch version loses the fence → a `lost` event.
  - **Amplified ~2–3× by replica fan-out** (each logical loser emitted on every replica) and the dashboard
    previously didn't dedup → the inflated "600". Storage (WAL) cuts it ~10× by avoiding a fresh-node full
    catch-up.
  - **Fix applied to the tool:** distinguish epoch-fence (calm "rebalance" metric, expected) from true
    same-epoch conflicts (the red alarm). The alarm no longer false-fires on rebalance churn.
  - **Open fero optimisation (efficiency, not correctness):** re-shipping superseded records is wasted
    bandwidth+CPU that grows with the log. Either **compact the log** (drop versions dominated by a higher
    epoch — root [IDEAS](../../IDEAS.md) "Bounded memory & compaction") or make catch-up **epoch-aware**
    (skip records a key already has a higher-epoch winner for — "Catch-up & anti-entropy hardening").
    *Hook:* `recordsSince`/`resync` (log + resource/index.ts) + `applyInbound` LWW.

## Surfaced during Slice 3 (the push-hook)
- **Batched/off-tick emit to cut active overhead.** Watching multiplies per-write latency ~3× (measured) — the cost of building a ProvRecord + a data-proxy slot write + sink delivery on each commit. The hard requirement (zero cost when *unwatched*) holds, but the *watched* path could be cheaper: push to a plain ring synchronously (near-zero) and flush to the streamed proxy in batches on a microtask, moving the proxy/sink work OFF the synchronous write+replicate path. *Hook:* `resource/observe.ts` `push()` + a `queueMicrotask` flush. Guard with `observe.perf.ts` Test II.
- **Deterministic LWW-loser / dedup-drop generation.** Losers and dedup-drops are rare BY DESIGN (the write-gate stops a minority diverging; single-sequencer ordering stops re-delivery; anti-entropy is digest-driven). A deterministic positive test needs a true split-brain (dual writable majorities) — a **Slice-5 war-game** scenario. *Hook:* a tuned `cluster()` partition where both sides keep quorum.
- **Provenance ticker kind-filter.** The `applied` fan-out (R−1 events per write) dominates the ticker. Add clickable kind chips that toggle row visibility (CSS `[data-kind]` hide), so the user can focus on `local`/`lost`/`forwarded`. *Hook:* a reactive `stream.hide` flag bound to a container class; data render event binding.

## Surfaced by the full-project review (fixes landed with DECISIONS O; these are the open residues)
- **Multi-bridge push-leg revival blind spot.** The bridge detects its dead `__observe` leg via the
  snapshot's `observing` flag (it holds a sub against `observing:false` ⇒ re-subscribe). With TWO+
  bridges on one cluster, bridge B keeping a node's gate armed masks bridge A's dead leg (`observing`
  stays true). Exact fix needs per-subscriber liveness — e.g. a client-side sub-death notification when
  the dialed peer bounces (pairs with the root-IDEAS "Pending RPCs and the subs map are not failed over
  on peer disconnect"). *Hook:* `ensureObserve`/`dropObserve` (bridge.ts) + transport `subs`.
- **Grid event-buffer overflow is a silent drop-oldest.** Past `EVENT_CAP` (4000) between flushes the
  ring overwrites oldest in O(1) — correct and bounded, but unreported. Ship a `dropped` count with the
  `records` batch (needs a small `web/app.js` shape change). *Hook:* `account()`/`flushEvents()`.
- **`marks` payload grows with origin churn.** The snapshot ships the full raw `seen` digest per poll —
  O(origins×partitions) under scoping; dead-origin debris accumulates until compaction/GC prunes it.
  Cap or summarize once a deployment shows real pressure (the lag panel needs only live-origin marks).
  *Hook:* `makeSnapshot` marks + the `isLiveK` filter (bridge.ts).
- **Wire-watched perf coverage.** `observe.perf.ts` A/Bs the in-process watched path (~3×); the
  WIRE-watched path (a real `__observe` socket subscriber: + frame encode + socket write per event)
  is exercised functionally but not perf-gated. *Hook:* observe.perf.ts Test II + a real client sub.

## Multi-resource / multi-cluster / scale-out
- **Multi-resource view** — observe several fero resources from one dashboard. *Hook:* bridge dials per `(name, server)`; tab per name.
- **Multi-cluster merge** — several clusters in one pane. *Hook:* multiple bridges → one SSE multiplexer keyed by `(cluster, uuid)`.
- **Cluster-side gather inspect (thousands of nodes)** — make `__inspect` fan out over the cluster's own gossip/anti-entropy and return a rollup, so the bridge dials ONE node for the whole-cluster view instead of O(N) connections (removes the single-bridge SPOF/bottleneck). *Hook:* the Q3 `read()`-as-gather / decomposable-aggregate path applied to diagnostics ([DECISIONS Q3]). **Deliberately NOT v1 — rationale:** gather wins only the large-N connection-count axis and loses the axes that define a debugger — (1) it goes BLIND during a partition (the gather node sees only its own side, so the rollup hides the split — the #1 scenario the tool exists for), (2) it depends on the very machinery under test (gossip/AE/view), so it's wrong exactly when that's the bug, whereas direct-dial depends only on each node's pure-read `__inspect` + a socket, and (3) it inherits Q3's open fan-out/partial-result hardening. Direct-dial and gather share the snapshot type + aggregation tier + dashboard, so gather lands later as a drop-in *source adapter*, zero throwaway. Flip-condition: a deployment where only a single edge node is network-reachable (firewall/NAT) — then gather is the only option and the partition blind spot is the accepted cost.
- **Multi-vantage observer** — to see both sides of a real partition, merge snapshots from bridges placed in each partition-prone segment. *Hook:* SSE multiplexer keyed by uuid; distinguish `unreachable-from-observer` per vantage.
