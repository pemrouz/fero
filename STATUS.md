## Bugs

What happens, where, and the fix if one is known. The evidence behind each line (probes, file:line, transcripts) is in the old ledgers, `git show 0055e6e:ISSUES.md` and `git show 0055e6e:IDEAS.md`, or in the commit the line names.

### Kernel

- **A survivor stalled longer than the knock window turns a clean stop into a crash.** When a member presses Ctrl-C it asks the others to vote it out. Since the knock window (V4-39, [docs/DESIGN-LEAVE.md](docs/DESIGN-LEAVE.md) §10.7) it keeps asking for as long as it is connected to a member that is not itself leaving, up to `leave.ms` (8 s by default: 16 heartbeats, the tune row `leaveWindow`), so a survivor stalled for a few seconds still reads the request and votes, and the stop is clean; with no such member connected it waits four heartbeats and goes, as before. A survivor stalled past the window still wakes to a leaver that is gone and sees a crash; with two members that is permanent. `sim/leave-sweep.test.ts` pins it both ways: with the survivor's process paused (the sweep's stall now) every one of the 100 stall schedules is live at the default window (25 wedged before under that model, 36 under the old slow-survivor model, which stays beside it and wedges 20 now, 1 at a 64-tick window); with the pauses tripled past the window 22 wedge, all safe, and a 64-tick window makes them live again; the 100 cut-and-restart schedules are live on 90 (87 before), the 10 left being pairs cut apart inside the window with nobody else to knock at, a survivor cut from a leaver whose vote it needs, and a restarted leaver beside a read-only survivor, which a longer window does not change. The window has one cost the design did not foresee, the next line. No ballot rule moved, so the three splits of today's kernel (the two lines after it) are untouched; they are the release page's: the rule for "a vote above my view" is written in full, reviewed four times and measured on a scratch kernel ([docs/DESIGN-LEAVE.md](docs/DESIGN-LEAVE.md) §10.10; V4-41): a vote warns only when it is for a view two or more members apart from the voter's own, so a leave, a join and a one-suspect eviction hold nobody; a held member is read-only and uncounted by any stayer; its release is the proposer's word where the proposer is there and supersession by the held view's own majority where it is not, never a clock; the holds ride the HELLO and the PULL. On the scratch kernel the three splits and the genesis split close and every family is safe; two minors and two nits from the fourth re-check are open in §10.10 for the build (`docs/leave-release.diff`), which is next. The parked branch is `w1/membership`.
- **A LEAVE knock reopens an aged-out leave ballot ahead of an evictable suspect.** A cluster running on a bare majority (three members with one crashed and not yet voted out, five with two), whichever member stops, the lowest included: the lowest stayer's leave ballot leaves the leaver out, so its new set needs a dead member's vote and can never commit. Each time it ages out (`proposalAge`, 10 ticks) the leaver's next knock lands between ticks and re-proposes it before the tick's eviction branch runs, so the dead member is never evicted while the leaver knocks. The leaver waits the whole knock window (about 8.5 s at the default cadence, past `fero.spawn`'s 5 s grace, so the verdict reads `null`) and goes unclean, where before V4-39 it went at the fifth tick; the stayer sits `minority` in the old view either way, so the outcome is no worse, only slower. Measured on the sim at heartbeat 50 with the third member cut 200 ms before the stop: `left` b=0 at 250 / 850 / 3250 ms for a 4 / 16 / 64-tick window; clean in one tick once the eviction ran first. The README says to let the eviction finish first. The fix is proposer logic (a knock must not reopen an aged-out leave ballot while a given-up suspect is evictable), outside the knock window's zero-risk scope: the leave chain's work.
- **Two suspects evicted in one ballot can commit two views at one epoch, and both sides write.** The one-view-per-epoch argument counts two majorities of ONE old view, and the writable split at different epochs holds only by arithmetic for a ballot that changes one member. The eviction branch (`kernel/membership.ts`, the tick) drops every given-up suspect in one proposal; at five members with two suspects the new view's writable majority (two) and a stale majority of the old view (three) need only five voters. A voter cut or crashed right after its grant never learns the view it voted for, keeps the old view with the two "suspects" as a reachable majority, and either leads them into a view of its own (`evictTwo`: `n01@3{n01,n02}` beside `n03@4{n03,n04,n05}`) or grants a never-voted member's higher ballot over the old view (`evictTwoB`: `n01@3{n01,n05}` beside `n02@4{n02,n03,n04}`); the sim's own monitor fires at epoch 3 either way. `sim/leave-harness.test.ts` pins both as the seeds they split on (1, 2, 4, 5 of 5; the one-evictee control never splits); the parked branch has them too. Found 2026-10-10 by the I-20 harness and its reviews. The root is a node acting on a view below a vote it has spent; the kept-ballot line below has the same root. The rule for it is written and measured ([docs/DESIGN-LEAVE.md](docs/DESIGN-LEAVE.md) §10.10, V4-41): a vote for a view two or more members apart from the voter's own closes its gate, keeps its link out of every stayer's count (a stayer learns the holds from the HELLO and the ask, so there is no round trip in which it counts the held member), and lets it lead and grant only a ballot joint over that view; the far side of the cut stays read-only, the CP answer, until the cut heals or the view's proposer disowns the ballot. On the scratch kernel `evictTwo` and `evictTwoB` are 0 of 5, `releasedEarly` (the same shape with the grant 200 ms old at the commit and the VIEW lost) 0 of 5, `freshLink` (the held member's link flaps) shows one writable view at every point; a release on a clock reopens all of them. No kernel line has changed; the build is next.
- **A ballot kept across an install commits two members apart from the view it was kept across; at four members that is two views at one epoch, both writable.** `#proposal.old` is fixed when the ballot opens, `install()` keeps a proposal whose epoch is above the new view, and a voter grants any epoch above its own view because the PROPOSE frame carries no base epoch. On a one-member path it settles to one view (the double-vote scenario of 2026-10-08). On a two-member path it does not: aa and bb lose each other and duel at 2; bb wins `{bb,cc,dd}@2`; aa, refused, escalates to `{aa,cc,dd}@3` over view 1, installs view 2 evicted, keeps the ballot, and commits it on cc's and dd's grants given from view 2. aa and dd then write at 3 beside bb and cc at 2 (one view per epoch intact, so the monitor sees nothing), and once the cut chains give up `{aa,dd}@4` commits beside `{bb,cc}@4`. Pinned RED TODAY in `sim/leave-harness.test.ts` as `keptBallot`, one fixed schedule on real Nodes. Found 2026-10-10 by the third review of [docs/DESIGN-LEAVE.md](docs/DESIGN-LEAVE.md) §10, which had called the shape undrawn. Same root and same rule as the line above ([docs/DESIGN-LEAVE.md](docs/DESIGN-LEAVE.md) §10.10): a PROPOSE carries the epoch of the view it is over and a voter refuses a ballot over a view below its own, so this ballot dies at cc and dd, and aa, which now drops every ballot on an install, re-proposes over the view it holds; in the reversed order (`keptBallotReversed`, the grant one apart and the install two apart) the hold re-read at the install holds cc and dd instead. Measured safe on the scratch kernel in both orders, no split at any epoch. No kernel line has changed.
- **After tombstone GC and compaction, a removed row can come back from a short lane.** Three unscoped nodes: one writes a row (its lane stays one record long) and leaves cleanly, and the row moves to another node, which removes it and then writes a hundred rows of its own. Once tombstone GC and compaction both run, the remove is gone from the remover's lane, but the old write is still the last entry of the leaver's lane. So a joiner ends with the row present while the members have it absent, and a durable member comes back from its own disk with it. The release of a stamp has to take every lane's dead entry for that cell with it. Pinned RED TODAY in `sim/scale-probes.test.ts` with no test seam; M1 and M3 see it. The fix moves unscoped trajectories, so it lands by its own decision ([docs/DESIGN-SCALE.md](docs/DESIGN-SCALE.md) §14 Q7).
- **A write from an evicted member beats a newer remove after a heal.** Four unscoped nodes. The owner commits a write whose frames die in the kernel buffer as its links sever, and it is cut off and voted out. Another node removes the row in the next epoch, the three remaining nodes GC the tombstone, and the link heals. The three then hold the old write (stamped in the earlier epoch) and the fourth holds nothing. A remove stamped later lost to a write stamped earlier, and the cluster is split for good. Pinned RED TODAY in `sim/scale-probes.test.ts`: M6 is red at the release itself, M1 and M3 at the heal. Same path to a fix as the short lane: lane accounting before a release.
- **On a scoped cluster, one forwarded write can commit twice across an ownership move.** In the scoped sweep (A3, seed 6) a forwarded field remove commits at the owner; 1.5 ms later the orphan cut takes every one of the owner's links down, before the commit's fan-out or its WACK left it. The issuer retries, the new owner commits it again, and after the heal both commits stand; the attempt-exactly-once monitor fires. The latch is not the gap (it already feeds the dedup window); no other node ever held the first commit. It is the zombie's class, a commit stranded on a cut-off owner, so its fix belongs with the zombie's. A remove committed again can erase a newer write. Pinned in `sim/scoped-sweep.test.ts` KNOWN_UNSAFE. Stage 2 of the scale design (V4-40) did not fix it: A3 seed 6 is safe now only because every scoped trajectory moved and its 1.5 ms window between the commit and the cut does not open; the same class shows at `FERO_SCOPED_SEEDS=12` on A2 seeds 9, 10 and 12 (and on A2 seed 15 on the base tree too), and A2 seed 9 is the pin in `sim/scoped-sweep.test.ts` KNOWN_UNSAFE now, so the class stays in every battery. A3 seed 10 still shows a partition not held where the ring assigns it. The fix is the zombie's.
- **A rolling change of a cluster key or of the secret splits the cluster until every member runs the new value.** The contract refuses a peer whose `heartbeat.ms`, `replicas`, `methods`, `validation` text or ring differs, and the door refuses a peer with another secret, so changing either is a full stop and start of every member and client; there is no rotation window ([docs/DESIGN-DOOR.md](docs/DESIGN-DOOR.md) §4). Loud and correct where the drift used to be silent. The derived client key changes with the secret, so every client restarts too.
- **A discovered target that never admits holds genesis at the lowest-uuid member for good.** Genesis waits there for links ≥ hosts, and hosts counts the discovered set, so a squatter the directory handed out, or a dead entry, blocks the first view until it goes away. A V4-3 property, with or without a door; found by the door family (`sim/door.test.ts`).
- **A dialer that loses the door's refusal notice re-dials a wrong-secret peer for one bounded chain before it gives up.** The DOOR notice is best-effort (on loopback it arrived on 70 of 70 attempts); a bare close while proving is a link loss, so a lost notice costs one redial chain, then the ordinary give-up and heartbeat revival, with no `refused` row on the dialer: the acceptor's `bad-proof` row and line say what happened. In the sim the notice is never read unless the pair's delay is fixed (its close model lands the close before a frame shipped in the same step), so the sim proves the lost-notice path.
- **A client refused `uuid-taken` on the open path redials for good, one journal row per dial.** An open node ships no notice and admits a HELLO on arrival, so a client that holds a member's uuid (a stray `FERO_UUID`) reads a bare close, which is a link loss: it redials at its redial cadence (about every 50 ms at `redial.ms` 30), elects the member as its feeder for a millisecond or two each time and loses it on the close, and the member journals one `doorReject` row per dial beside the link rows, so its 4096-row ring turns over in minutes. Nothing is ever fed; with a secret the client reads the notice and parks, so only the open path loops. Found by the V4-36 review ([docs/DESIGN-DOOR.md](docs/DESIGN-DOOR.md) §3, the dated note). A fix needs a word the open path does not have today, or a park on the dialer's side keyed on a repeated close of an admitted link.
- **A secured crossing dial costs one extra dial.** When two secured members dial each other at once, the dialer whose accepted link the peer closed as the duplicate starts a redial chain before its own dialed link's proof lands; the extra link is closed as a duplicate at once. Harmless, inside the 104,050 pin.
- **The journal's 4096 ring fills in about 34 minutes when two mis-keyed or mis-configured members re-dial each other every 500 ms.** Each dial writes a `doorReject` or `contractReject` row at both ends, the cadence `nameReject` has today. Stated, not fixed.
- **Drain at R=1 when the new holder crashes mid-drain.** The leaver goes at the next tick with `left(false)` and `undrained` counted, and the rows are lost unless it kept a `dir`. Waiting for a re-range while another member is reachable kept every row in a 5-seed probe but ended just inside the 16-tick bound. The owner's call (DESIGN-SCALE's note of 2026-10-10).
- **A scoped leaver whose vote never came back counts nothing.** Still in its own view when its bound ends (`leaveTicks` + 1 with no member linked that could answer, `leaveWindow` + 1 with one), it goes like a crash: nothing froze, so there is no orphan to drain and `undrained` reads 0 even though at R=1 its rows go with it. The README and `api/types.ts` say so (V4-38). A fix needs the leaver to know the ballot's fate, which is the leave chain's work.
- **A torn digest answer's resume costs CPU that grows with the square of the ship.** Since V4-40 a feeder whose digest answer tears (its paused queue overflowing partway through the ship, the shell stepping `pause` inside a send) stops at the tear and resumes at the drain, so no row is lost; but every drain round re-walks and re-encodes the rest of the torn lane, ships about one socket buffer, and queues 256 more frames only to clear them. Measured at a spoke's first connect over a sparse lane: 20k records 11 rounds and 224 ms, 160k records 93 rounds and 15.8 s of feeder CPU, against 493 ms untorn. The fix (the third re-check of V4-40): find the resume point by binary search and encode only what ships; never overflow the queue on purpose, stop at the next frame when it is full; keep the answer resumable until its reply has left the queue.
- **A clear that takes a queued reply makes a spoke in resync download everything again.** When a digest answer's last frames and its r=0 reply still sit in the paused queue, any later clear (the drain digest's own overflow right after a resume, or one live tap-forward) takes the reply with it; the spoke stays in resync and the `h: 1` re-ask brings the feeder's whole held subset again from zero. No row is lost; the cost is one full re-download per such clear, and under steady writes a big ship's last round usually sits in the queue. Same fix as the line above (keep the answer resumable until its reply has left the queue). Found by the third re-check of V4-40.
- **Two granters cut from the proposer before the first VIEW form a second view at genesis, at the same epoch the proposer's side reaches next, and both sides write.** At genesis the old set is empty, so a ballot needs only a majority of its new set, and a granter at epoch 0 whose vote is spent at 1 proposes over the empty set at 2. At five members: aa installs view 1 on bb's and cc's grants; dd and ee are cut from aa, bb and cc before the VIEW; aa evicts them (`{aa,bb,cc}`@2) and dd, the lowest of its side, forms `{dd,ee}`@2 with ee: two views at epoch 2, both writable at the quiet point. It needs hostless nodes (a mesh, or a listener given no hosts); with a static host list every node proposes over its full host set, so no Sim family draws it. Pinned RED TODAY in `sim/leave-harness.test.ts` as `genesisSplit`, one fixed schedule on real Nodes. Found 2026-10-10 by the third review of [docs/DESIGN-LEAVE.md](docs/DESIGN-LEAVE.md) §10.10. The rule of §10.10 closes it on the scratch kernel (a genesis vote is a hold n members apart from the empty view; dd's ballot is joint over the five and needs three), at the cost named there (`genesisProposerAndGranterDie`). No kernel line has changed.

### The api

- **An array-valued row's screen can still depend on arrival order.** V4-18 folds object, number, null and string rows the same everywhere. data, though, writes into arrays like objects: an index write replaces the element, a field inside an element lands, and a non-index key becomes a hidden property; and data refuses to remove an array's own key, so the kernel makes no repair inside an array. Write the spliced array. Removing an array's own element is refused before it commits, for the shape the issuing node shows, or, when a scoped member cannot see the row, for the shape its owner shows: the lens throws for `delete data.g[0]`, and `methods.remove({ key: ['g', 0] })`, a client's relayed remove or a scoped non-holder's forwarded remove rejects `sparse-hole` (V4-28; the owner re-check of V4-33). One gap still commits a tombstone that shows nothing: a remove sent in the same batch as a still-pending write that turns the row into an array is judged on the old shape.
- **A spoke's write can still wait for ever when its feeder dies between the WACK and the tap.** A client's write to a partition its feeder holds is settled by the value arriving on the tap (V4-7). If the feeder's link dies after the WACK cleared the attempt and before the record reached the tap, the relay's bookkeeping dies with it; the spoke fails over, and the value reaches it only if its next feeder holds the partition. A scope change at a live feeder is covered (V4-33's rescope settlement); a feeder death is not. Evidence: [docs/DESIGN-SCALE.md](docs/DESIGN-SCALE.md), the second-review note of 2026-10-09.
- **On the open path, a dup-link close of my own dial starts a generic redial chain toward a member I am still linked to.** The peer can close my duplicate dial before its HELLO reaches me, so the close looks like a link loss and arms the ordinary ten-try chain toward a live peer; each try is another duplicate dial. It is bounded and no longer affects eviction: if the member then crashes, its linkDown replaces that chain with the member chain (V4-34). Pinned by kernel/node.test.ts 'a member that dies while a GENERIC chain toward it is running'.
- **A handler that makes a view and returns a plain value leaks that view (the I-29 residue).** Each such call leaves one dead filter on the source, and data works it out again on every commit. It cannot be released safely today: a view the handler dropped looks the same as one it keeps for its next call (`cached ??= ctx.data.filter(…)`). Releasing it froze the cached view silently, so that change was backed out (V4-16). A fix needs to know when the handler's handle becomes unreachable (a FinalizationRegistry over the handles minted inside a handler). The proxy-return path has a cousin: a view a handler caches on its first call and returns there is released after that call.
- **The refusal lines can skip a line on a journal ring overflow.** They are fed from the composer's post-step journal cursor, so a burst past `journal.cap` inside one step loses the line; the row is the contract.
- **A view whose function throws on a replicated row crashes the client process.** A client's `cafe.data.filter((c) => c.mood === 'hungry')` meets a row the server set to `null`. data leaves the row out of the view and names it in an `AggregateError` after the commit (data's SCHEDULE_VERSION 5, 2026-10-11; before it, the throw also stopped every later write in the process), but fero lets that error out of its projection (`#apply` → `applyRec`, [api/data.ts](api/data.ts)) into the frame handler, which rethrows anything that is not a `FrameError` ([kernel/node.ts](kernel/node.ts)); nothing catches it and Node exits with code 1. A local write that brings the row throws at the assignment instead, after it has committed. Found 2026-10-11 with a server and a client on a private rendezvous. A fix catches the error at the projection and reports it without stopping the node: the record has committed and data has already left the row out.

### Directory, config, shell

- **A server booting right after the directory host died once failed with `c.methods.lookup is not a function`.** Not reproduced in 30 runs, nor in the new race test (api/directory.test.ts: the host SIGKILLed, a new server 0-500 ms later, every time it takes the directory over). The stated cause is ruled out: a client's `methods` hands out a handle for any name, and a sub sent before any primary is held and replayed. The only way left is the directory's client compose coming back as a server. Directory.start() now checks that: if it recurs, fero() fails with `#directory: the directory client composed as a <role> — its methods have no lookup (I-19)`. Next to probe: a survivor racing the newcomer for the port (the EADDRINUSE path in `#tryHost`).

### The debugger

- **A scoped capture paints every node `differs`.** With `replicas` set, each member holds only its own rows, so the fingerprints differ by design. The header says `differs (in flight)` and every node row carries an amber pill (the `scoped` scenario shows it). Compare per row among its holders, not one fingerprint per node.
- **Known limits of the replay**, accepted and written in the fold header of `tools/debug/model.mjs`. A link killed by a fatal frame drop can win a client's primary re-election in the replay for one round trip. Scoped and durable nodes open empty stream lanes with no journal row, so a reborn durable writer's links and streams show `@ end` instead of replaying. `synced` flips one row early when the same step also ships a catch-up.
- **On a scoped capture, a client and a member that left are still painted `never-arrived`.** The holder lists are as of capture end, and only a current member of the writer's view can be called `not a holder`. A client's writes are judged by the old rule, and so is a member that left cleanly or was voted out: both get red stops for rows they were never meant to hold. A fix needs each client's feeder and what it holds, and a rule for non-members. Also, the links-and-streams replay does not fold a hand-off's watermark jump, so a node that acquired a row shows its links and streams `@ end` under rewind.

- **Kernel.** Suspicion watches link liveness, not ping round trips, so a hung-but-connected process looks alive. When the pending-write queue overflows, the oldest write is dropped and counted; how big the queue should be against the retry horizon has never been measured. A lying disk that lies only about the newest row of a lane escapes the hole detector; chained durable marks would close it. On an UNSCOPED cluster anti-entropy digests still go full mesh every tick, O(n²) frames; a scoped cluster has the stage-2 handshake instead (V4-40). A drain that follows a drop made before a spoke's resync ask arrived costs one extra ship of the feeder's held subset (the drain digest's `h: 1` says the ask may have gone unanswered; when it was answered the spoke re-asks once more than needed: one per drop event, never per tick). A full-mesh pause burst can drop a whole link queue at once.
- **Scoped replication (the M6 leftovers).** Designed on 2026-10-09 in [docs/DESIGN-SCALE.md](docs/DESIGN-SCALE.md) (a three-proposal panel): the member heartbeat digest stops on scoped clusters and holders announce floors to co-holders; compaction un-pins behind a frontier over the holders' crash-stable floors; tombstone GC runs under a census, a holder quorum and lane accounting; a clean leave drains first. Six stages, the harness first; the owner took every default of its §14 on 2026-10-09 (V4-31). Stage 0, the harness, landed the same day (V4-32): monitors M1-M10 with a planted-violation test each, the adversaries A1-A11 and a mutation runner in `sim/scoped-sweep.ts` (2 seeds per family in the battery, more with `FERO_SCOPED_SEEDS`), the frame tally, the two unscoped holes pinned red today, today's counted floors (idle n(n−1) DIGEST per tick; 300 writes 1,067 HAVEQ; one join at n=30 2,446 HAVEQ), and the restored-floor cap. Stage 1 landed in two parts: without the drain (V4-33: the `acked` effect, the owner re-check, the indexes with M4 live and pin R1), then the drain (V4-38, 2026-10-10): a scoped member's clean stop holds `left` until every reachable new holder has attested what it held (the shed bar, one predicate `covers` shared by the shed, the drain and the stall surface), bounded by the tune row `drainTicks` (16); past the bound, or with nobody to drain to (the last member), it goes at once with an `undrained` journal row, `destroy()` resolves false and `cluster.me.undrained` counts the partitions; a leaver whose own view already dropped it drains even when the survivors' echo was lost (the verdict stays false); M9 is green. Known cost (the owner's call, DESIGN-SCALE's note of 2026-10-10): at R=1 a new holder that crashes mid-drain takes the rows it was about to receive; the leaver reports it honestly. Stage 2 landed the same day (V4-40): the member heartbeat digest retires on scoped clusters; an owner announces the floors it stamped to its co-holders in one batched HAVEQ per link at the next tick, a never-answered co-holder is asked every tick, the orphan poll and the probe round go to the partition's holders only, and a sweep over `aeFan` (tune row, 8) co-holder links per tick re-proves every pair within ⌈c / aeFan⌉ ticks; admit and drain digests still sync a link but ship nothing to a member; HAVEQ carries `d` (durable floors), `g` (gapless) and `x` (released), HAVEA answers `g: 1` and `x: 1`. Idle at n=100 R=3 with 3,000 rows: 1,600 frames and 250 KB per tick where it was 9,900 frames and 2.93 MB (P1-P3 in `sim/announce.test.ts`). A node now teaches its pre-latch base mid-latch (two holders ahead on different lanes used to deadlock once no digest shipped suffixes). A spoke's resync asks once on any link speed (a server's drain digest toward a client carries `h: 1`, the one r=1 a spoke in resync re-asks on), and a digest answer whose ship tears resumes at the drain from the first frame the socket did not take (`Link.torn`), the reply after the whole ship — a torn ship is a late reply, never a missing one; its two costs are bug lines above. Next: stage 3 (compaction), which requires this stage. A delete forwarded to the owner for a row that does not exist there commits a tombstone for nothing, as `methods.remove` of an absent key does; stage 4's accounting should count it. The list as it stood: Tombstone GC stays pinned while scoped. Distributed `sum` / `max` / `avg` instead of the materialize-first throw. Spokes subscribe to what they watch, not the whole shard. Explicit-undefined cells across the gather. A push-based claim stream. Chunked transfer for oversized partitions. Smaller HAVEQ bodies. The unscoped two-teacher race. Shed only on durable marks. Disjoint partial sums. Nicer remote handles.
- **Directory.** A failure detector over client links, so a hung watcher's entry does not live for ever. One directory client per process instead of one per instance. A `#directory` node cannot be attached by the debugger: a system compose takes no `diag.allow`. An askable directory (a routable rendezvous) is unauthenticated; with a secret set, a wrong address it hands out is refused at the door (V4-30), not prevented. A failed lookup is never re-subscribed, and on this box's own directory a server's next successful register clears its lookup `error` while the lookup stays dead. `localish()` does not treat IPv4-mapped spellings (`[::ffff:127.0.0.1]`) as loopback.
- **Sim and scale.** Monitor passes walk every lane even when nothing changed (about 15 ms per pass at n=100); scope the walk to the node that stepped. Scale goldens are tied to (n, writes, seed); failure captures at n=100 are triage-grade only.
- **Door.** A rotation window, `secret: [new, old]`. A server signing key, so a client can tell a member from another client-key holder: the one limit the derived client key leaves open ([docs/DESIGN-DOOR.md](docs/DESIGN-DOOR.md) §15); until then a stale or forged directory entry, or a typed host, can feed a client, and a member is never fooled. TLS at the shell: everything after the handshake is cleartext, and a relay at a typed static host is not caught; the handshake runs unchanged under it. A client-key terminal for the 18-secret rung. `secret.client` accepts 16 characters or more though a real key is always 43; an exact check would catch a mis-copied key at `fero()` instead of at the door. The `FERO_CONFIG=off` note matches only the exact spelling of `FERO_SECRET_CLIENT`. The sim's close model orders a close before frames shipped in the same step, so a dialer in the sim never reads a notice unless the pair's delay is fixed; ordering it behind them would move every golden and the 59,500 pin, a decision, not a fix.
- **Debugger.** Ship journal deltas over the DIAG wire instead of whole journals. Cache unchanging log entries between rebuilds (never below the node's base). A paged state read with a torn-snapshot marker for a state map over one frame (a too-big answer is already named `frame`). `topologyAt` still joins a reborn writer's rows to the bare lane on purpose: it is the one truthful producer of a replay refusal three suites rely on. A capture that mixes resources (the user's nodes beside the `#directory` nodes) paints every node `differs`, because the fingerprint, the cells and the routes assume one resource; group them by the node's name, which every capture now carries (the `#` tag beside the label still shows).
- **data (the sibling).** Streaming a windowed sort needs the mirror keyed by position. Apply inbound records per frame instead of per record. Slim `fold.ts`'s cell-isolation armor.
- **Config.** optcascade wishes: a declared-keys mode for the prefixed form, per-key provenance with the file path, a `strings` list so `--fero.uuid 12345678` survives.
- **Open questions.** Cross-partition ordering beyond the recipe (transactions?). AsyncIterator methods.

## Decided

One line each. The full record, with the context and the rejected options, is [docs/DECISIONS.md](docs/DECISIONS.md); the v3 decisions (V3-1 to V3-21) and the carried v2 rejections are there too.

- **V4-1** fero v4 runs on data v4. fero owns the write surface: the lens traps a write before data sees it.
- **V4-2** Role by declared act: a bare `fero(name)` is a client; any server marker makes a server. `f.snapshot` is the sync read. A node's identity comes back from its `dir`.
- **V4-3** Discovery is the per-box `#directory` at `127.0.0.1:3376`. A server binds a free port and registers; `#` names are reserved.
- **V4-4** The relay validates: `seams.validation` runs on a client's relayed write too, and a refusal is a terminal reject with the reason.
- **V4-5** `methods:` is the one spelling for hosted methods and the door. Spokes are views: they never teach a server.
- **V4-6** A clean `destroy()` leaves by ballot, so two members survive a clean stop. Amended: "nothing to leave" needs evidence.
- **V4-7** No ghost: a write shows when it commits, never before. The optimistic copy is gone.
- **V4-8** Ctrl-C is a clean stop, built in. The cluster view folds in one batch. The examples carry no plumbing.
- **V4-9** `fero.spawn` is public. A check meets the box directory. A stop untracks when it settles.
- **V4-10** One config door: `--fero.<key>` > the call > `FERO_<KEY>` > `fero.opt.ts` > the default. Nested lowercase keys. `optcascade` is the one dependency.
- **V4-11** A README is the terminals; a screen is one line or one frame.
- **V4-12** The example series is complete: a story file is a driver, an app may run past ten lines, a check runs every file its README names, no slow tier.
- **V4-13** One ledger. This page holds the status, the bugs, the ideas and the decisions index; the full records live in `docs/`; 42 obvious warts were fixed instead of filed, and the fixes that touched the public surface are listed there. Amended 2026-10-08: a client follows its feeder's view even to a lower number, so `cluster.epoch` on a client is its feeder's number (I-23).
- **V4-14** The ring hash is fnv-1a finished with fmix32, and it is part of the wire contract; mixed versions are unsupported before 1.0.
- **V4-15** The lower uuid opens the admit digest exchange, so a join ships each missing row once; the formation count re-pins 69,400 → 59,500.
- **V4-16** The method plane: a live scalar arrives as `{ value }`; a subscription has a `ready` per attempt and an `onError`; a kernel outcome on an assignment fails the call; a plain-value handler keeps its views.
- **V4-17** The shell's `start()` always settles (typed `stopped` / `started`); a store whose boot record failed mid-life is condemned on restart.
- **V4-18** Overlapping cells: the newer stamp wins across depth. A whole-row write (or row remove) hides every field cell stamped at or below it; a field stamped above it shows on top, in every arrival order, on the screen and in the scoped gather; a row a removed field had made up goes away; a write of ours that commits settles committed once its echo arrives, even when the echo is refused. Arrays are the limit.
