## Bugs

What happens, where, and the fix if one is known. The evidence behind each line (probes, file:line, transcripts) is in the old ledgers, `git show 0055e6e:ISSUES.md` and `git show 0055e6e:IDEAS.md`, or in the commit the line names.

### Kernel

- **A survivor stalled longer than the knock window turns a clean stop into a crash.** When a member presses Ctrl-C it asks the others to vote it out. Since the knock window (V4-39, [docs/DESIGN-LEAVE.md](docs/DESIGN-LEAVE.md) §10.7) it keeps asking for as long as it is connected to a member that is not itself leaving, up to `leave.ms` (8 s by default: 16 heartbeats, the tune row `leaveWindow`), so a survivor stalled for a few seconds still reads the request and votes, and the stop is clean; with no such member connected it waits four heartbeats and goes, as before. A survivor stalled past the window still wakes to a leaver that is gone and sees a crash; with two members that is permanent. `sim/leave-sweep.test.ts` pins it both ways: with the survivor's process paused (the sweep's stall now) every one of the 100 stall schedules is live at the default window (25 wedged before under that model, 36 under the old slow-survivor model, which stays beside it and wedges 20 now, 1 at a 64-tick window); with the pauses tripled past the window 22 wedge, all safe, and a 64-tick window makes them live again; the 100 cut-and-restart schedules are live on 90 (87 before), the 10 left being pairs cut apart inside the window with nobody else to knock at, a survivor cut from a leaver whose vote it needs, and a restarted leaver beside a read-only survivor, which a longer window does not change. The window had one cost the design did not foresee — a knock that reopened an aged-out leave ballot ahead of an evictable suspect — fixed by V4-60: the eviction rides with the leave. No ballot rule moved with the window. The three splits it left (two suspects evicted at once, the kept ballot, genesis) are closed by the release rule (V4-55, [docs/DESIGN-LEAVE.md](docs/DESIGN-LEAVE.md) §10.10): a vote for a view two or more members apart from the voter's own holds it, read-only and uncounted by any stayer, until that view commits, its proposer disowns the ballot, or that view's own majority supersedes it — never a clock. What that costs is the next line. The parked branch `w1/membership` is history.
- **A held member is read-only until the view it voted for is settled, and three shapes never settle it without an operator.** Since V4-55 a member that voted for a view two or more members apart from its own (a two-suspect eviction, a ballot over an older view, a genesis grant) is `held`: read-only, and not counted toward anyone's majority, until that view commits, its proposer disowns the ballot (it answers the held member's ask with a NACK when it holds neither the ballot nor a view at or above it; the ask goes to the proposer whether or not it is a member), or a ballot that view's own majority consents to supersedes it — when no membership change would open that ballot, the lowest live member opens it, the same members at the next epoch, joint over the holds, only when it can commit and only with every member of its view linked (a lost member's eviction is the ballot instead); it opens it on a hold a linked member named and on its own, when the proposer it granted is out of the view and unlinked (a linked one is asked and disowns). A flap, a crash of the proposer and every one-member change hold nobody, and a disown releases a hold in one round trip. Three shapes stay read-only for good, because from the held member's seat dead and cut look the same (the CP answer, DESIGN-LEAVE §10.10.4): the far side of a cut (`evictTwo`, until the cut heals); the third granter of a two-evictee ballot whose proposer and other granter died for good, with the two evictees it leads (`proposerAndGranterDie`: three live, linked members read-only); and the one survivor of a genesis ballot beside a newcomer or the others reborn memory-only (`genesisProposerAndGranterDie`: nothing forms). The remedy is the operator's, as for the crash-at-two class: forget the dead, or start the survivor fresh. Pinned in `sim/leave-harness.test.ts` as the exact end states. A held member asks its proposer once per heartbeat per member link while held; nothing is sent while nobody holds anything.
- **A same-name host that refuses this node's secret or cluster contract holds genesis at the lowest-uuid member until the operator acts — loudly.** The first view waits for every host that might be one of us (V4-60). A target that answers for another resource NAME is not waited for: another resource for good, permanent and symmetric (it refuses every member of mine the same way), so no half of one resource ever counts the other out while it could still join. A target that refuses this node's proof or its contract is the same process with a config fix: counting it out let each consistent half of one host list form its own writable view at epoch 1, and fixing the config then linked the halves but never merged them (one view per epoch) — two clusters under one name for good, where the base waited and then formed one view (DESIGN-DIRECTORY §13, the review's probe). So it waits, and the refusal line says so once per target: `fero('shop'): refused 10.0.0.5:4000 — its secret differs from this node's — the first view waits on it`. The remedy is the operator's: fix the mismatch, or take the address out of `hosts`. A dead STATIC host waits the same way, silently (a closed port and a cut look alike from the dialer's seat); a dead directory entry is dropped by the directory's failure detector within its bound (§12). One more residual: a static host list whose members disagree on the NAME forms one cluster per name, silently (`nameReject` prints nothing since V4-3), and renaming one half later cannot merge them — the renamed half must start without its dirs.
- **After every member stops cleanly one at a time, only the last to stop can bring the cluster back — decided, not changed.** Each leaver's dir holds the view it saw last, one it is not in ({bb,cc}@2, {cc}@3), so the first two back sit `joining` at {cc}@3 until cc returns; pinned on the sim (`sim/leave-harness.ts` stopsOneByOne) and on real sockets and WALs (`tests/stops.test.ts`). No kernel rule can re-form them safely: the last view's only voter is cc, and a re-form without it splits the moment cc comes back from its dir and self-ballots its solo view (dead and down look the same). The remedy is an operator word, `reform`, specified in DESIGN-LEAVE's note of 2026-10-12 and not built: a restart flag that re-forms over the admitted set with an empty old set, its hazard named. The same word is what "forget the dead" means for the crash-at-two class and V4-55's three frozen shapes.
- **After tombstone GC and compaction, a removed row can come back from a short lane.** Three unscoped nodes: one writes a row (its lane stays one record long) and leaves cleanly, and the row moves to another node, which removes it and then writes a hundred rows of its own. Once tombstone GC and compaction both run, the remove is gone from the remover's lane, but the old write is still the last entry of the leaver's lane. So a joiner ends with the row present while the members have it absent, and a durable member comes back from its own disk with it. The release of a stamp has to take every lane's dead entry for that cell with it. Pinned RED TODAY in `sim/scale-probes.test.ts` with no test seam; M1 and M3 see it. The fix moves unscoped trajectories, so it lands by its own decision ([docs/DESIGN-SCALE.md](docs/DESIGN-SCALE.md) §14 Q7).
- **A write from an evicted member beats a newer remove after a heal.** Four unscoped nodes. The owner commits a write whose frames die in the kernel buffer as its links sever, and it is cut off and voted out. Another node removes the row in the next epoch, the three remaining nodes GC the tombstone, and the link heals. The three then hold the old write (stamped in the earlier epoch) and the fourth holds nothing. A remove stamped later lost to a write stamped earlier, and the cluster is split for good. Pinned RED TODAY in `sim/scale-probes.test.ts`: M6 is red at the release itself, M1 and M3 at the heal. Same path to a fix as the short lane: lane accounting before a release.
- **On a scoped cluster, one forwarded write can commit twice across an ownership move.** In the scoped sweep (A3, seed 6) a forwarded field remove commits at the owner; 1.5 ms later the orphan cut takes every one of the owner's links down, before the commit's fan-out or its WACK left it. The issuer retries, the new owner commits it again, and after the heal both commits stand; the attempt-exactly-once monitor fires. The latch is not the gap (it already feeds the dedup window); no other node ever held the first commit. It is the zombie's class, a commit stranded on a cut-off owner, so its fix belongs with the zombie's. A remove committed again can erase a newer write. Pinned in `sim/scoped-sweep.test.ts` KNOWN_UNSAFE. Stage 2 of the scale design (V4-40) did not fix it: A3 seed 6 is safe now only because every scoped trajectory moved and its 1.5 ms window between the commit and the cut does not open; the same class shows at `FERO_SCOPED_SEEDS=12` on A2 seeds 9, 10 and 12 (and on A2 seed 15 on the base tree too), and A2 seed 9 is the pin in `sim/scoped-sweep.test.ts` KNOWN_UNSAFE now, so the class stays in every battery. A3 seed 10 still shows a partition not held where the ring assigns it. The fix is the zombie's.
- **A rolling change of a cluster key or of the secret splits the cluster until every member runs the new value.** The contract refuses a peer whose `heartbeat.ms`, `replicas`, `methods`, `validation` text or ring differs, and the door refuses a peer with another secret, so changing either is a full stop and start of every member and client; there is no rotation window ([docs/DESIGN-DOOR.md](docs/DESIGN-DOOR.md) §4). Loud and correct where the drift used to be silent. The derived client key changes with the secret, so every client restarts too.
- **A dialer that loses the door's refusal notice re-dials a wrong-secret peer for one bounded chain before it gives up.** The DOOR notice is best-effort (on loopback it arrived on 70 of 70 attempts); a bare close while proving is a link loss, so a lost notice costs one redial chain, then the ordinary give-up and heartbeat revival, with no `refused` row on the dialer: the acceptor's `bad-proof` row and line say what happened. In the sim the notice is never read unless the pair's delay is fixed (its close model lands the close before a frame shipped in the same step), so the sim proves the lost-notice path.
- **A client refused `uuid-taken` on the open path redials for good, one journal row per dial.** An open node ships no notice and admits a HELLO on arrival, so a client that holds a member's uuid (a stray `FERO_UUID`) reads a bare close, which is a link loss: it redials at its redial cadence (about every 50 ms at `redial.ms` 30), elects the member as its feeder for a millisecond or two each time and loses it on the close, and the member journals one `doorReject` row per dial beside the link rows, so its 4096-row ring turns over in minutes. Nothing is ever fed; with a secret the client reads the notice and parks, so only the open path loops. Found by the V4-36 review ([docs/DESIGN-DOOR.md](docs/DESIGN-DOOR.md) §3, the dated note). A fix needs a word the open path does not have today, or a park on the dialer's side keyed on a repeated close of an admitted link.
- **A secured crossing dial costs one extra dial.** When two secured members dial each other at once, the dialer whose accepted link the peer closed as the duplicate starts a redial chain before its own dialed link's proof lands; the extra link is closed as a duplicate at once. Harmless, inside the 104,050 pin.
- **The journal's 4096 ring fills in about 34 minutes when two mis-keyed or mis-configured members re-dial each other every 500 ms.** Each dial writes a `doorReject` or `contractReject` row at both ends, the cadence `nameReject` has today. Stated, not fixed.
- **Drain at R=1 when the new holder crashes mid-drain.** The leaver goes at the next tick with `left(false)` and `undrained` counted, and the rows are lost unless it kept a `dir`. Waiting for a re-range while another member is reachable kept every row in a 5-seed probe but ended just inside the 16-tick bound. The owner's call (DESIGN-SCALE's note of 2026-10-10).
- **A methods test failed once in its setup and hung the battery.** In the wave-5f merged battery, api/methods.test.ts 'a sub that fails AFTER its first frame' failed in 3.5 ms, before any of its steps; the detail was lost because the file then never exited: every test there built its servers with `pair()` before its own try, so the failed setup left a server listening, and the battery sat for about seven hours. `pair()` now destroys what it started before it rethrows, so such a failure is loud and fast. The cause of the one failure is not proven (most likely a free port taken between picking and binding; it passed in every lane battery and in five lone runs). A battery-wide guard (a per-file time limit, or `--test-force-exit`) would bound any such hang; not adopted, since it would also hide leaks the suites should catch.
- **A row the spoke kept across a resync end leaves the screen at the fold's end and comes back if its record reaches the feeder later; a partition shed while the spoke's link was paused leaves the screen at the heal and comes back whole with the same answer if the feeder holds it again.** Since V4-62 a scoped spoke's resync end keeps the cells of the partitions its new feeder is folding (the reply's `f`), and a kept cell's life is bounded by three clauses: the fold's end judges every one of them at once (a cell the fold did not bring is gone); every way out of in flight sends a word, the link-loss one included (a blip onto the same feeder resyncs at the re-admit); and a word a clear takes is owed and said again at the answer that heals the link, each at its own place in the order: a shed's word BEFORE that answer's ship, unfiltered, and the answer's start lowered, on every lane, under the lowest entry of every partition the word named, held or not, so the ship re-sends them WHOLE (the partition's rows leave with the word and come back with the same answer, at its reply: one flicker inside the exchange, on a cold path, never a ghost); an end AFTER the reply, only while the partition is held. The clause-1 cost: a record still in flight to the feeder at the fold's end (the owner's frame to it on a paused link that outlasted the failover, the ask, the answer and the fold; or a frame lost on the way and brought by a later repair, a double fault) leaves the screen at the end and returns when it lands or when the repair folds — one bounded vanish-and-return, which M12 reads. Taken on purpose over waiting for the lane, which had no bound (a lane whose owner died with the spoke's first feeder never moves again), and over any filter on the owed shed word, which was wrong in three rounds and would leave a removed row for good once stage 4 releases tombstones. Named in the wave-6c note of docs/DESIGN-SCALE.md. The clause-1 cost is reached by no seeded schedule and is not pinned (the 56-run probe judges no such cell). The owed shed word is reached since V4-67: the scoped sweep's A14 owes and pays it on 71 of seeds 1-72 and judges spoke = feeder at the heal exchange's end, with the partition away, coming back or held again, so the heal-exchange flicker is judged on random schedules. Of the whole re-send, A14 judges one shape: the leapfrog onto a lane the clear took nothing from, with one entry of one partition (seeds 32 and 120 of 200). It does not reach two entries of the partition on the surviving lane, two partitions named in one word, or a repair latch open at the heal, and it never judges the fold's end. Those stay pinned in kernel/client.test.ts only, which asserts spoke = feeder at the exchange's end before any beat on each of its shapes (the held shape; the leapfrog at two queue sizes; two entries of the partition on the surviving lane; two partitions named in one word, the first, the second or both taken back; a repair latch open at the heal on the leapfrogged partition, fed but not held; the second named back first and leapfrogged on a lane the first has no entry on).
- **A spoke can show a removed row for one event when a clear lands inside its feeder's fold forward.** Since V4-62 a latch fold's forward reaches a spoke between FEED `b` and `e` and lands as one apply, so an older value of a row and its later remove no longer show as two events (A12 seed 4). One hole is left: on a paused client link one frame short of full, `b` fits, the forward's first frame overflows the queue, and the clear takes `b` with it. `Link.flush` ships on after a clear on a client link, so the forward's later frames survive with no group open and land one event each at the drain, the row showing between them; the end state is right. Found by the lane's eighth review (its probe R8-2, saved with the lane's probes; not pinned). A fix would ship a fresh `b` into the emptied queue when a clear takes a `b` whose `e` it did not take.
- **A fresh member's `data:` seed brings back a seed row the cluster deleted, and the copies then disagree.** Three members share a seed; one row is deleted and its tombstone is collected (`tombstoneGC`, within a heartbeat); a fourth member with an empty fold applies the same seed at boot and joins. After it joins, the three old members show the deleted row again and the new member does not, at one view of four, writable, in 2 runs of 2 on v4 63e0679. The seed's own rule ("fresh keys ride in", `api/index.ts` at the seed) cannot tell a key the cluster never had from one it deleted. Every scale-out of a seeded resource hits it. Found 2026-10-12 by the platform page's review (`~/.claude/plans/fero-platform/spikes/review/probe-seed.ts`).
- **A server redials the listen a client's HELLO claimed when that client's link drops.** kernel/node.ts linkDown sets the redial target of every accepted link to `link.listen`, and a client's link is no exception. fero's own clients send '', so nothing is dialed, but any client can point the server's redial chain at an address it picks: a probe with `l: 'evil.example:80', r: 1` armed a redial there (JK.redial, 10 ms) the moment the link dropped. Since V4-64 that address is at most 259 bytes. Found by the bounds lane (wave 7).
- **At epoch 1 or later, a write issued from a tap while a server applies its own commit is committed a second time.** kernel/write.ts #commit calls node.commit(run) while the run's attempts are still in `pending`, so the tap's write re-enters #drain and commits the same attempts again under a new seq; #remove runs only after. In a two-server probe, one outer write plus one tap write grows the log by 3, not 2 (dup-commit.test.ts in the wave-7 apilines review probes; red on v4 517b26b too). The values converge (the copies land in issue order), but the attempt is logged and replicated twice, and taps run once more. A fix takes the attempts out of `pending` (or marks them) before node.commit. Found by the wave-7 apilines lane (2026-10-22); not pinned.

### The api

- **An array-valued row's screen can still depend on arrival order.** V4-18 folds object, number, null and string rows the same everywhere. data, though, writes into arrays like objects: an index write replaces the element, a field inside an element lands, and a non-index key becomes a hidden property; and data refuses to remove an array's own key, so the kernel makes no repair inside an array. Write the spliced array. Removing an array's own element is refused before it commits, for the shape the issuing node shows, or, when a scoped member cannot see the row, for the shape its owner shows: the lens throws for `delete data.g[0]`, and `methods.remove({ key: ['g', 0] })`, a client's relayed remove or a scoped non-holder's forwarded remove rejects `sparse-hole` (V4-28; the owner re-check of V4-33). One gap still commits a tombstone that shows nothing: a remove sent in the same batch as a still-pending write that turns the row into an array is judged on the old shape. And only the last named field set on an array shows: the substrate keeps one, on a node's own view (applyRec) and in the gather's union (applyStreamRec), so a row `[1, 2]` with field cells `f` and `h` shows `[1, 2, h: …]` or `[1, 2, f: …]` by which was applied last, and the union's object depends on the order its answers came in (a keyed read takes its own answer last, a whole read first), against V4-18's rule that it does not; no reply carries an array's named fields, so every read answers `[1, 2]` (the wave-7 apikeyed lane's round-5 differential, 2026-10-22).
- **A spoke's write can settle before its value shows when its feeder dies between the WACK and the tap and the next feeder lags the record.** A spoke is a client fed by one scoped server. Since V4-43 its feeder names the owner's lane in the receipt (`l`), and at the failover's resync end the spoke settles, through `acked`, every write its new feeder's download did not bring. A next feeder that holds the partition but has not yet received the record looks the same as one that does not hold it, so the write resolves first and the value shows as long afterwards as that feeder lags the record (43-48 ms in the pinned schedule). A later write of ours to the same cell can also resolve before its value shows (narrow). Since V4-62 the pieces to tell the two apart are there: the resync reply's `f` names the partitions the new feeder is folding, and the spoke's lanes after the re-download say which partitions it feeds, so the end could wait for the tap for a write whose partition is named or fed. Not built: a client's awaiting entry does not keep the attempt's partition (kernel/write.ts `#awaiting`, `p` is '' there), and `sim/feeder-death.test.ts` 'known cost' pins today's order.
- **On the open path, a dup-link close of my own dial starts a generic redial chain toward a member I am still linked to.** The peer can close my duplicate dial before its HELLO reaches me, so the close looks like a link loss and arms the ordinary ten-try chain toward a live peer; each try is another duplicate dial. It is bounded and no longer affects eviction: if the member then crashes, its linkDown replaces that chain with the member chain (V4-34). Pinned by kernel/node.test.ts 'a member that dies while a GENERIC chain toward it is running'.
- **A view a handler makes some other way than ctx.data is not tracked.** Release by the collector (V4-54) covers views made through ctx.data and views made off them. A handler that closes over the resource and calls f.data.filter(…) still leaves that view behind when it returns a plain value. When it returns the view, the old eager release runs, cousin included: a view cached that way and returned on the first call goes stale. A raw handle taken from the internals door (`unwrap`) is never marked as held by outside code, so a deduped view reached that way can be released under it. Evidence: api/views.test.ts covers ctx.data only; disposeMinted in api/substrate.ts is the old path.
- **Under a view module code ever reached, a handler's view goes only if data never reuses its operator.** Once module code touches f.data.top(10), even once, a handler's ctx.data.top(10).sum(fn), .distinct(fn), .some(fn) or .length(fn) stays for good. Data does not reuse those either, but fero picks the private operators by name (filter, map, reduce, group, tap, to, union, intersect, except: PRIVATE_OPS in api/substrate.ts), so any other operator is treated as one module code might reach. It is never released early, only never. Release also waits for the collector: a dropped view is worked out on every commit until a GC finds it.
- **A view a handler passes as a reactive argument can stay for good.** In `ctx.data.gt('n', ctx.data.avg('n'))` data hangs an effect on the avg, so the collector refuses it while the gt lives; when the gt goes later nothing tries the avg again, and it stays on the source (a per-key cache of 23 such chains, cleared, left 46 nodes where v4 left 69). Late, never early. A fix remembers the argument views a call passed in and tries them when the view they feed is released. Found by the third I-29 review (2026-10-11).
- **After data cuts a write loop, this node shows one write less than its kernel holds.** A tap that writes on every change runs until data's cap (1000 commits); data drops the queued projections, so the proxy reads the second-to-last value while the kernel and every other node hold the last, until the row changes again. Older than V4-47; since then fero says so in one stderr line instead of throwing at the assignment. A fix refuses a runaway chain of tap-issued writes in Bind.issue, below data's cap, before the kernel stamps them.
- **A row read by reference can be changed in place, and then the copies disagree.** `f.snapshot`, `await data` on an unscoped node, and the rows a view hands out are the stored values themselves, not copies. A program that changes `f.snapshot.r.n` changes what this node holds and serves from then on, because its kernel and its log hold the same object; every other copy keeps the old value (in V4-52's design probe the writer read 1, the server and a late client 99). Since V4-52 a write keeps fero's own copy, so this is the one way left for a stored value to change. A fix freezes or copies rows where they are handed out; it costs every read, so measure that first. Found by V4-52's design (2026-10-12).
- **A read of a row during a handover parks only what that row's own folds heard.** Since V4-65 a keyed read gathers only its row's partition and folds it into the live union for that row alone, so a keyed read of ANOTHER row no longer refreshes this one (base's keyed read was a whole refresh, which every row heard). So in the skew window (the old holder has shed, the new holders are still acquiring), a read of row `a`, keyed or whole, parks only what `a`'s own keyed reads and the live generations heard. A newer value of `a` that only a keyed read of `b` heard is lost, and the read returns the older one (s4/s4-cross-path.test.ts test 3 in the wave-7 apikeyed review probes: { x: 1 } where base gives { x: 2 }); a delete of `a` that only such a read heard is not applied, so `a` reads present at its older value (s5/s5-cross-remove.test.ts: { x: 1 } where base gives undefined); and a row that only such a read heard of reads absent. No read goes back past an earlier read on the same node, because this node never showed what only the other row's read heard (s5/s5-multi-sim.test.ts: 0 of 842 row reads, as base). This holds for every read of the row, not only the first. Found by the wave-7 apikeyed lane's round-2, round-4 and round-5 reviews (2026-10-22); not pinned.
- **A whole read can miss a row it has not seen before when that row's handover ends during the gather.** The whole read (api/fold.ts #refresh) takes this node's own `rows` answer first. If this node finishes taking a row over while the other answers travel, and the old holder sheds before it answers, no answer claims the row, and the gather shows the resource without it (whole-midread.test.ts in the wave-7 apikeyed review probes; red on v4 517b26b). Taking the own answer last only moves the gap: when this node is the row's OLD holder and sheds during the gather, after the new holder answered while still taking it over, the row is missing then (s3/s3-whole-mirror.test.ts in the same probes, run with s3/fold-last.ts: the old-holder shape is green with the own answer first and red with it last, the new-holder shape the other way round). In one gather this node can be one row's old holder and another row's new one, so no single order is right; a fix needs a new rule (for example this node's answer taken at both ends and merged, with an argument that the merge never brings back a delete). A row the gather has already seen, in a live generation or in a keyed read of that row, parks, so only a row new to it is hit: the first gather on a node, or a row written since. A one-shot whole read then answers without a row that exists. The keyed read is not hit: there this node is the row's owner, never its old holder (V4-65, KEYED MID-READ). Found by the wave-7 apikeyed lane's round-3 review (2026-10-22); not pinned.
