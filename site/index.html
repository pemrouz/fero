one assignment, one record

Plain assignment replicates.

await fero(name) gives you a live object. Read it like a plain object. Change it by plain assignment. Derive live views from it. Every process that opens the same name sees the same object, on one box or across a cluster.

fero's own examples build a shop, a chat room, a kanban board and a ledger. Each row (a top-level key) has one owner: the one server that stamps its writes. Your assignment becomes one record. The owner gives it a stamp: the number of the view (the agreed list of servers, which only a vote changes), a counter and its name. Then the record lands on every copy. Nothing shows before it commits, and nothing merges.

one row, one writer

Kill the owner.
The write still lands.

Each row (a top-level key) has one owner: the one server that stamps its writes. Kill it, and a write to its row waits. Nothing shows early.

The other servers vote the dead one out: a new view (the agreed list of servers). A survivor takes the row and gives the write its stamp: the view number, a counter and its name. The write lands on every live copy. That needs a majority: two servers cannot survive a crash, so run three.

        Each line is one frame a node sent, taken apart by kernel/codec.js. The ◆ line is the owner stamping the record. Grey lines are repeats. A write is sent again when no receipt has come back in time, and c1's server passes each resend on, unless it owns the row. A record is sent again when a digest says it is missing. A digest is a node's list of the highest counter it holds from each writer, and it can be out of date by the time it lands.

          Each run is a separate simulation, so nothing here touches the cluster above. A crash waits: the survivors redial the dead server until they give up, and only then vote.             06
            On the wire
            
      
            
        A write crosses the wire as one frame: a short header, the writer, the counter it starts at, the view
        number, then the records. Most also carry the attempt: who issued the write, and its own counter for it.
        Below is a real frame from the cluster above, taken apart by
        kernel/codec.ts. The owner writes these same bytes to its write-ahead log (the WAL, its log on
        disk), and the page checks them byte for byte. When a node comes back, one side opens with a digest, the
        highest counter it holds from each writer. The other sends only what is missing, then answers with its own
        digest, and the first side fills that gap too.
