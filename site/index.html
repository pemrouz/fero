Shared live objects for Node

Plain assignment replicates.

await fero(name) gives you a live object. Read it like a plain object. Change it by plain assignment. Every process that opens the same name sees the same object, on one box or across a cluster.

Its examples build a chat room, a kanban board and a ledger. This page runs a tiny cat café.

import { fero } from 'fero'

const cafe = await fero('cafe')
// every copy hears luna purr
cafe.data.luna = { mood: 'purring' }

What the kernel did

The last few things the kernel did, newest last, each with its simulated time. The page runs the kernel, not fero() itself: a button posts the record that an assignment becomes. A commit line ends with the write's stamp: the view's number (the view is the agreed list of servers), a counter, and the owner that stamped it. The counter is a clock, not a count: a server moves it up to the biggest number it has seen, so gaps are normal. After a restart it starts above every number the server used before.

    01

    How a write travels

    Your write goes to its row's owner first, then to every copy.

    Each top-level key, like luna, is a row. Each row has one owner: the one server that takes the row's writes first and puts them in order.

      How the owner puts writes in order

      The owner stamps each write with three things: the view's number (the view is the agreed list of servers), a counter, and its own name. The counter is a clock, not a count: a server moves it up to the biggest number it has seen, so gaps are normal. After a restart it starts above every number the server used before. Each copy keeps, for every field, the write with the biggest stamp. So every copy picks the same write, and nothing merges.

      02

      Break it

      Kill a server. The others carry on.

      Writes need the side with more than half the servers. Reads never wait: every copy keeps serving what it has. Try each one on the live café above.

      n01✕down n02★new owner n03 luna

      Crash a server

      The others vote it out after about four seconds at the defaults. A write made meanwhile waits, then lands.

      n01 n02 n03cut offreads ✓ · writes wait

      Cut one off

      The cut-off server keeps serving reads, and catches up when the split heals.

      disk n01✓back n02 n03 catches up

      Restart from disk

      Run the same file again with dir: './state' and it comes back as itself, with its rows from its disk, then catches up.

      n01 n02^Cleft n03 vote

      Stop it with Ctrl-C

      It asks the others to vote it out, and they carry on without it. Start it again and it asks to join.

      Run three servers, each with a disk. A cluster of two survives a clean stop, but not a crash.

      03

      Start

      Two files: a café and a visitor.

      Starting data (a seed) makes fero a server. A bare fero('cafe') is a client: it finds the server by name, keeps its own copy, and sends its writes up.

      04

      Why trust it

      — runs on an unreliable, simulated network: every copy ends the same, every time.

      The simulator runs the same kernel code as the servers, on a network with uneven delays, repeated messages and, on every other run, a cut that heals. It checks eleven rules after every event. Every random choice comes from one number, so a failing run replays exactly.

          How this runs in your tab

          This page loads the data library from npm when you scroll here.

          fero's kernel runs here too, on a simulated network. The page cannot run fero() itself (that needs Node's sockets), so client c1 posts the record each assignment becomes. The library starts from that client's copy, then takes every change that reaches it through lane(), the same call fero makes when a change reaches a copy.

          After every change, the page also checks each cat in that copy by hand, in plain JavaScript, and compares the rows with the filter's.
